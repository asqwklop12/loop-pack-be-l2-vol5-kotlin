## 1. 요구와 범위

### 1-1. 기준 문장

> **"구매자는 주문 확정 전에 보유 쿠폰을 적용할 수 있고, 확정된 할인 금액은 나중에 바뀌지 않아야 한다."**

### 1-2. 이 문장이 답하지 않는 것

| # | 빠진 것 | 처리 |
| --- | --- | --- |
| 1 | "확정"이 무슨 사건인지 | 결제 직전, 낼 금액이 고정되는 시점으로 잡았다 (4-1) |
| 2 | 결제와 확정이 같은 사건인지 | 확정이 결제 직전이므로 다른 사건이다 (4-1) |
| 3 | 이미 쿠폰이 붙은 주문에 다른 쿠폰을 요청하면 | 거절한다 (INV-002) |
| 4 | 운영자도 적용할 수 있는지 | 없다. 구매자만 (4-0) |
| 5 | 재요청과 만료가 겹칠 때의 우선순위 | 만료가 우선한다 (INV-005 · INV-006) |
| 6 | 주문 취소 시 쿠폰이 복원되는지 | 쿠폰만 복원하고 주문 기록은 유지한다 (4-1) |
| 7 | 할인액이 원금을 넘을 때 | 원금까지 잘라내고 성공한다 (INV-003) |
| 8 | 할인 계산 방식 (정률 / 정액) | A-6 |
| 9 | 쿠폰 적용 단위 (주문 / 상품) | A-5 |
| 10 | 만료 판정의 경계·측정 시점·시간대 | A-4 |
| 11 | 주문과 쿠폰이 어떤 상태 값을 갖는지 | 4-1 |
| 12 | 동시 요청이 들어올 때의 동작 | 4-3 |
| 13 | 남의 쿠폰으로 요청했을 때의 응답 | 없는 쿠폰과 같다 (4-2) |
| 14 | 쿠폰이 어떻게 발급되는지 | 범위 밖 |

### 1-3. 제약

| ID | 제약 |
| --- | --- |
| C-1 | 한 주문 · 한 쿠폰 |
| C-2 | 외부 결제 시스템 없음 |
| C-3 | 기존 `commerce-api` 안에서 구현하며 현재 응답 형식을 바꾸지 않는다 |

## 2. 요구 분류

> - **요구 사항(F)** — 기준 문장에서 근거를 가리킬 수 있다
> - **설계 결정(A)** — 요구에 없어 직접 정했다. 되돌릴 때의 파급을 함께 적었다

### 2-1. 요구 사항

| ID | 내용 | 근거 | 연결되는 불변식 |
| --- | --- | --- | --- |
| F-1 | 구매자는 **자신이 소유한** 주문에, **확정 전에만**, **보유한** 쿠폰을 적용할 수 있다 | 기준 문장 전반부 | INV-001 |
| F-2 | 확정된 할인 금액은 이후 정책·가격 변화에도 바뀌지 않는다 | 기준 문장 후반부. UC-01 종료 조건 | INV-004 |

### 2-2. 설계 결정

| ID | 결정 | 되돌릴 때 영향 범위 | 연결되는 불변식 |
| --- | --- | --- | --- |
| A-1 | 한 주문에는 쿠폰 **한 장만** 적용한다 | 복수 쿠폰을 허용하면 요청이 `couponId` 단수에서 배열로 바뀌고, 할인 합산 순서와 중복 사용 규칙이 새로 필요하다. 저장 구조도 1:1 에서 1:N 으로 확장된다 | INV-002 |
| A-2 | `finalAmount = originalAmount - discountAmount` 이고 할인액은 **0 이상 원금 이하** | 상한을 풀면 `finalAmount` 가 음수가 될 수 있어 환불·정산이 음수 금액을 다뤄야 한다. 하한을 풀면 금액이 늘어나는 쿠폰이 되어 "할인"이라는 이름이 맞지 않는다 | INV-003 |
| A-3 | **쿠폰이 유효한 동안** 같은 주문·쿠폰 재요청은 **저장된 결과**를 성공 응답으로 돌려주고 효과를 늘리지 않는다 | 실패로 바꾸면 오류 코드가 하나 늘고, 요청자가 재시도 대신 조회로 가야 한다 | INV-005 |
| A-4 | 만료 판정은 **요청을 받은 시각** 기준이다. 그 시각은 요청 진입 시 한 번만 찍어 처리 전체에 넘긴다. `expiresAt` 은 **배타적 끝**이며 시각은 **KST 고정**이다 | 기준 시각을 저장 시각으로 바꾸면 경계에서 결과가 달라진다. `expiresAt` 을 포함 끝으로 바꾸면 부등호를 `<` 로 고치고 저장된 값을 전부 마이그레이션해야 한다. 해외 서비스로 확장하면 사용자 시간대별 판정이 필요해진다 | INV-006 |
| A-5 | 쿠폰은 **주문 단위**로 적용된다. `originalAmount` 는 주문 총액이며 품목별로 쪼개지 않는다 | 상품 단위로 바꾸면 **기술** — 할인액 저장이 1:N(품목별)이 되고 부분 취소 시 배분 규칙이 필요하며 INV-003 을 다시 써야 한다. **제품** — 상품·카테고리마다 정책이 필요해 쿠폰 수가 늘고, 어느 쿠폰이 어디에 되는지 사용자가 알기 어려워져 최대 할인 조합 자동 선택이 사실상 필수가 된다. **운영** — 정책 관리 부담과 문의가 늘어난다 | INV-003 |
| A-6 | 할인은 **정액만** 다룬다. 금액 타입은 `BigInteger`, 단위는 원(KRW) | 정률을 도입하면 `originalAmount × rate` 에서 소수가 생겨 절사 규칙(방향 · 단위)을 정해야 하고, 무한 노출을 막을 `maxDiscountAmount` 도 필요해진다. 정액은 값 자체가 상한이라 둘 다 없어도 된다 | INV-003 |

> 주문과 쿠폰의 상태 값은 조건이 아니라 모델 정의이므로 **4-1** 에 적었다.

## 3. 현재 시스템의 응답 규약

| # | 입력 | status | `meta.result` | `meta.errorCode` | `data` |
| --- | --- | --- | --- | --- | --- |
| 1 | 존재하는 숫자 ID | 200 | `SUCCESS` | 키 없음 | 있음 |
| 2 | 숫자가 아닌 ID (`abc`) | 400 | `FAIL` | `Bad Request` | 없음 |
| 3 | 없는 숫자 ID (`-1`) | 404 | `FAIL` | `Not Found` | 없음 |
| 4 | 미매핑 URL | 404 | `FAIL` | `Not Found` | 없음 |

응답 본문:

```json
// 1. 존재하는 숫자 ID
{
  "meta": { "result": "SUCCESS" },
  "data": { "id": 1, "name": "관찰 대상", "description": "관찰용 설명" }
}

// 2. 숫자가 아닌 ID
{
  "meta": {
    "result": "FAIL",
    "errorCode": "Bad Request",
    "message": "요청 파라미터 'exampleId' (타입: long)의 값 'abc'이(가) 잘못되었습니다."
  }
}

// 3. 없는 숫자 ID
{
  "meta": {
    "result": "FAIL",
    "errorCode": "Not Found",
    "message": "[id = -1] 예시를 찾을 수 없습니다."
  }
}

// 4. 미매핑 URL
{
  "meta": {
    "result": "FAIL",
    "errorCode": "Not Found",
    "message": "존재하지 않는 요청입니다."
  }
}
```

### 여기서 나온 사실

**O-1** — `errorCode` 는 도메인 코드가 아니라 `HttpStatus.reasonPhrase` 다. 같은 status 를 쓰는 서로 다른 실패는 `errorCode` 로 구별되지 않는다. → 할인 API 의 여러 실패를 코드로 나눌 수 없다. **결정 1 이 여기 걸린다.**

**O-2** — 3번(없는 자원)과 4번(미매핑 URL)은 status·errorCode 가 같고 `message` 만 다르다. → INV-001("없는 주문과 구별되지 않는다")을 지키려면 **`message` 까지 같아야 한다.**

**O-3** — 성공 응답에는 `errorCode` · `message` 키 자체가 없다. null 필드가 직렬화에서 빠진다. → 성공 응답을 설계할 때 그 두 키를 `null` 로 넣는 형태를 가정하면 안 된다.

## 4. 액터 · 상태 · 불변식

### 4-0. 액터와 사용 장면

| 액터 | 이 흐름에서의 목적 | 이번 범위 |
| --- | --- | --- |
| 구매자 | 자기 주문의 결제 금액을 낮춘다 | **포함** — UC-01 의 주 사용자 |
| 운영자 | 고객 문의 대응, 보상 처리 | **제외** — 쿠폰 적용 권한이 없다. 대응은 재발급이며 그건 발급 흐름이다 |
| 정산 시스템 | 확정된 할인 금액으로 장부를 맞춘다 | **제외** — 확정 이후 흐름 |
| 판매자 | 자기 상품의 할인 부담을 확인한다 | **제외** — 쿠폰 적용 단위가 주문이므로 (A-5) |

```
Use case UC-01: 주문에 쿠폰 적용
주 사용자: 구매자
시작 조건: 구매자 소유 주문이며 아직 확정되지 않음
시작 사건: couponId 선택
성공 결과: 할인 결과 기록과 최종 주문 금액 반환
실패 결과: 주문 없음 / 소유자 다름 / 주문 확정 / 쿠폰 사용 불가
종료 조건: 성공한 할인 결과 기록은 이후 정책·가격 변화에도 동일
```

### 4-1. 상태 값

```
주문    PENDING ──확정──> CONFIRMED
        쿠폰 적용 가능      금액 고정 (INV-004)

쿠폰    ISSUED ──확정──> USED ──주문 취소──> ISSUED
        미사용           소진됨              복원
```

| 값 | 의미 | 이 계약에서의 역할 |
| --- | --- | --- |
| `주문.PENDING` | 아직 확정되지 않음 | 쿠폰 적용이 가능한 유일한 상태 (F-1) |
| `주문.CONFIRMED` | 확정됨 | 할인 금액이 고정된다 (INV-004) |
| `쿠폰.ISSUED` | 발급됐고 아직 안 씀 | 적용 대상이 될 수 있음 |
| `쿠폰.USED` | 확정된 주문에 소진됨 | 주문 취소 시 `ISSUED` 로 되돌아간다 |
| `쿠폰.orderId` | 지금 붙어 있는 주문. 없으면 `null` | **상태가 아니라 참조다.** 값이 있으면 다른 주문이 이 쿠폰을 쓸 수 없다. 동시 요청에서도 하나만 성공해야 한다 (4-3) |
| `쿠폰.expiresAt` | 이 발급분의 만료 시각 | **상태가 아니라 값이다.** 배타적 끝 · KST 고정 (A-4) |

```
CouponPolicy  id=1   "5,000원 할인"
   ├ UserCoupon  id=101  userId=1  expiresAt=…   ← 유저 1 만의 것
   └ UserCoupon  id=102  userId=2  expiresAt=…   ← 유저 2 만의 것
```

#### 소진 시점 — 적용 · 확정 · 취소

```
적용 (확정 전)   orderId = 100 기록.  status 는 ISSUED 그대로
확정             status = USED.  여기서 소진된다
주문 취소        orderId = null, status = ISSUED.  복원
```

### 4-2. 불변식

| 규칙 ID | 규칙 (상태 관계) | 출처 | 깨는 입력 (반례) | 기대 결과 | 책임 후보 |
| --- | --- | --- | --- | --- | --- |
| **INV-001** 주문 소유권 | 주문의 소유자와 다른 `X-USER-ID` 로 요청하면, 응답이 **그 주문이 없을 때의 응답과 구별되지 않는다** | F-1 | 사용자 A 의 주문 id 에 사용자 B 의 `X-USER-ID` 로 요청 | `404` / `Not Found` 이며 **`message` 까지 같다.** O-2 에서 message 로만 갈리는 것을 확인했으므로 status·errorCode 만 맞추면 존재가 새어나간다 | Order (소유자 판정) |
| **INV-002** 단일 쿠폰 | 확정 전 주문 하나에 연결된 성공한 쿠폰 적용 기록은 **최대 1개**다 | A-1 | 같은 주문에 쿠폰 X, Y 를 연달아 또는 동시에 적용 요청 | 두 번째 요청은 성공하지 않는다. 첫 쿠폰의 적용이 유지되고 기록은 1개다 | Order (적용 상태 보유) |
| **INV-003** 금액 관계 | `finalAmount = originalAmount - discountAmount` 이고 `0 ≤ discountAmount ≤ originalAmount` | A-2 | 원금 3,000 에 5,000 쿠폰 적용 | `discountAmount = min(쿠폰 할인액, originalAmount)` 로 잘라내고 성공한다. 음수 `finalAmount` 는 나오지 않는다 | 할인 계산 책임 |
| **INV-004** 확정 결과 보존 | 확정된 주문의 `discountAmount` 는 **쿠폰 정책을 바꾼 뒤 다시 조회해도 같다** | F-2 | 정책을 변경한 뒤 재조회 / 주문 취소 후 재조회 | 첫 확정 때와 동일하다. 취소해도 바뀌지 않으며 쿠폰만 복원된다 | Order (확정 결과 보유) |
| **INV-005** 재요청 | 쿠폰이 **유효한 동안** 같은 (주문, 쿠폰) 으로 두 번 요청하면, 두 번째도 성공하고 반환된 `discountAmount` 가 첫 요청과 **같다** | A-3 | 동일 요청 2회 연속 전송 | 두 번째도 200 으로 첫 결과와 같은 값을 반환한다. 할인 누적 없음. 오류를 주는 것도 위반이다 — 돌려줄 값이 없어지므로. 재요청 시점에 만료됐으면 INV-006 이 우선한다 | 적용 요청 처리 경계 |
| **INV-006** 만료 경계 | 요청을 받은 시각 `t` 에 대해 `coupon.expiresAt ≤ t` 이면 적용이 성공하지 않는다 | A-4 | 만료 1ms 후 도착한 요청 / 처리 지연으로 저장 시점엔 만료된 요청 / `t == expiresAt` 인 요청 | 요청 시각 기준으로 판정하며 그 시각은 진입 시 한 번 찍은 값이다. `t == expiresAt` 이면 만료다 — 배타적 끝이므로 | 쿠폰 사용 가능 판정 |

**쿠폰 소유권은 번호가 없다.** F-1 의 "**보유** 쿠폰"에서 나오며 규칙 문장으로 쓰면 이렇게 된다.

> 자신이 보유하지 않은 쿠폰으로 요청하면, 응답이 **그 쿠폰이 없을 때의 응답과 구별되지 않는다.**

INV-001 과 같은 이유다 — 403 을 주면 "그 쿠폰은 존재하는데 네 것이 아니다"가 새어나가 쿠폰 id 를 하나씩 넣어보며 탐색할 수 있다.

### 4-3. 동시 실행

불변식은 **어떤 실행 경로를 거쳐도** 참이어야 한다. 동시 실행도 실행 경로이므로 아래 불변식은 순차 요청과 동시 요청에서 같은 결과여야 한다.

| 불변식 | 동시 요청으로 깨지는 방식 |
| --- | --- |
| INV-002 | 두 요청이 각각 "아직 쿠폰 없음"을 읽고 서로 다른 쿠폰을 적용 → 기록 2개 |
| INV-005 | 같은 요청 두 개가 각각 "아직 적용 안 됨"을 읽고 계산·저장 → 할인 누적 |
| `쿠폰.orderId` | 두 요청이 각각 `orderId = null` 을 읽고 서로 다른 주문에 기록 → 한 쿠폰이 두 주문에 |

### 4-4. 검증 목록

| 규칙 ID | 입력 | 기대 결과 | 책임 후보 |
| --- | --- | --- | --- |
| INV-001 | 남의 주문 id + 내 `X-USER-ID` | `404` / `Not Found` / message 까지 없는 주문과 동일 | Order |
| INV-002 | 같은 주문에 두 번째 쿠폰 | `409`. 적용 기록이 1개를 넘지 않음 | Order |
| INV-003 | 원금 3,000 에 5,000 쿠폰 | `200`. `discountAmount` 3,000 · `finalAmount` 0 | 할인 계산 |
| INV-004 | 확정 후 정책 변경 → 재조회 | 값이 그대로 | Order |
| INV-005 | 동일 요청 2회 (쿠폰 유효) | `200`. 결과가 1회와 같음 | 요청 처리 경계 |
| INV-005 × 006 | 동일 요청 2회, 두 번째는 만료 후 | `400`. 만료가 우선 | 쿠폰 사용 가능 판정 |
| INV-006 | 만료 직후 요청 | `400`. 성공하지 않음 | 쿠폰 판정 |
| 쿠폰 소유권 | 남의 쿠폰 id + 내 `X-USER-ID` | `404` / `Not Found` / message 까지 없는 쿠폰과 동일 | 쿠폰 사용 가능 판정 |
| 동시 실행 | 위 입력들을 동시에 전송 | 순차로 보냈을 때와 같은 결과 | 4-3 |

## 5. 인터페이스

### 5-1. 외부 계약

| 항목 | 값 | 근거 |
| --- | --- | --- |
| Method / Path | `POST /api/v1/orders/{orderId}/discount` | 주문에 종속된 하위 자원 |
| 사용자 식별 | `X-USER-ID` 헤더 | 기존 API 관례 |
| Request body | `{ "couponId": <long> }` | C-1. 배열이 아닌 단수 |
| 금액 표기 | `BigInteger` · 원 단위 · KRW. 소수가 나오지 않는다 | A-6 |
| 성공 | 200, `meta.result = SUCCESS`, `data` 에 금액 3종. `errorCode` · `message` 키는 넣지 않는다 | O-3 |

성공 응답:

```json
{
  "meta": { "result": "SUCCESS" },
  "data": {
    "orderId": 1,
    "originalAmount": 50000,
    "discountAmount": 5000,
    "finalAmount": 45000
  }
}
```

실패 응답:

```json
{
  "meta": {
    "result": "FAIL",
    "errorCode": "Not Found",
    "message": "주문을 찾을 수 없습니다."
  }
}
```

### 5-2. 적용 시점과 고정 시점

이 API 는 **확정 전**에 호출된다 (F-1). 적용과 고정은 서로 다른 시점이다.

```
①  주문 생성                       상품이 묶이고, 아직 확정 아님
②  POST /orders/{id}/discount     쿠폰 적용.  결과가 저장된다
③  주문 확정                       이 시점의 값이 고정된다  (F-2 · INV-004)
```

### 5-3. 오류 의미

`errorCode` 는 `HttpStatus.reasonPhrase` 이므로 status 를 고르면 errorCode 가 따라온다 (O-1).

**검사 순서**

```
①  입력 형식        orderId · couponId · X-USER-ID      →  400
②  주문             존재 · 소유 · 확정 여부              →  404 / 409
③  쿠폰             존재 · 소유 · 만료 · 사용 여부        →  404 / 400 / 409
④  적용 가능 여부    이미 적용된 쿠폰이 있는지             →  409 / 200
⑤  계산             원금 초과 시 잘라냄                  →  200
```

앞 단계에서 실패하면 뒤 단계는 검사하지 않는다. 아래 표는 이 순서대로 정렬돼 있다.

| 상황 | status | errorCode | 규칙 | 요청자의 다음 행동 |
| --- | --- | --- | --- | --- |
| `orderId` 가 숫자가 아님 | 400 | `Bad Request` | — | 경로 수정 |
| `couponId` 가 없거나 숫자가 아님 | 400 | `Bad Request` | — | 요청 본문 수정 |
| `X-USER-ID` 헤더가 없음 | 400 | `Bad Request` | — | 헤더 추가 |
| 주문이 없음 | 404 | `Not Found` | — | 주문 목록 재조회 |
| 주문 소유자가 다름 | 404 | `Not Found` | INV-001 | 위와 message 까지 동일해야 한다 |
| 이미 확정된 주문 | 409 | `Conflict` | F-1 | 주문 상태 확인 |
| 쿠폰이 없음 / 내 것이 아님 | 404 | `Not Found` | F-1 | 보유 쿠폰 목록 재조회. 두 경우가 구별되지 않아야 한다 |
| 쿠폰이 만료됨 | 400 | `Bad Request` | INV-006 | 다른 쿠폰 선택 |
| 이미 사용된 쿠폰 (다른 주문에 씀) | 409 | `Conflict` | F-1 · 4-1 | 다른 쿠폰 선택 |
| 이미 다른 주문에 붙어 있는 쿠폰 | 409 | `Conflict` | 4-1 `orderId` | 그 주문을 확인하거나 다른 쿠폰 선택 |
| 이미 다른 쿠폰이 적용된 주문 | 409 | `Conflict` | INV-002 | 현재 적용된 쿠폰 확인. 변경은 지원하지 않음 |
| 같은 요청 재전송 (쿠폰 유효) | 200 | — | INV-005 | 없음 (첫 결과 수신) |
| 같은 요청 재전송 (쿠폰 만료됨) | 400 | `Bad Request` | INV-006 | 다른 쿠폰 선택. 만료가 멱등성보다 우선 |
| 할인액이 원금을 초과 | 200 | — | INV-003 | 없음. 원금까지 잘라내고 성공한다 |
