# 도메인 결정 — 2주차

흐름도는 `usecase.md`, 쿠폰 계약은 `../week1/order-discount-contract.md` 에 있다.


### 주문
- 재고는 **주문 확정 전**에 차감한다. 되돌리기 비싼 결제를 마지막에 두기 위해서다.
- 순서는 `주문서 제작 → 쿠폰 적용 → 재고 차감 → 쿠폰 소진 → 주문 확정 → 결제` 다.
- 주문서 제작 단계의 재고 확인은 안내이고, 성공·실패 판정은 차감 단계에서 한다.
- 확정은 **주문 확정**이며 금액이 고정되는 사건이다. 품목 단가·수량·합계·할인액·최종 결제 금액을 주문에 저장한다. 확정 후 조회는 다시 계산하지 않고 저장된 값을 읽는다.
- 결제 완료와 주문 완료는 시점이 같아도 같은 사건이 아니다. 결제 결과가 원인이고 주문 상태가 결과다. 두 값을 나란히 세팅하지 않는다.

### 주문 취소
- 확정 전 취소는 재고만 복원한다.
- 확정 후 취소는 `결제 복원 → 재고 복원 → 쿠폰 복원` 순으로, 차감의 역순으로 되돌린다.
- 취소해도 주문 기록은 남기고 상태만 바꾼다. 확정된 금액은 바뀌지 않는다.

### 좋아요
- 등록과 해제는 별도 API 두 개다. 하나의 토글 API로 만들지 않는다.
- 이미 그 상태여도 성공으로 응답한다. 같은 요청을 여러 번 보내도 결과가 같아야 한다.

### 삭제
- 브랜드·상품 모두 soft delete 로 `deletedAt` 을 기록한다.
- 삭제된 브랜드·상품은 없는 것으로 취급한다. 조회·주문·좋아요에서 제외하며, 삭제됐다는 사실을 응답으로 구분해 알리지 않는다.
- 브랜드는 **삭제되지 않은 상품이 0개일 때만** 삭제한다.
- 상품은 **재고가 0일 때만** 삭제하며, 그 상품의 좋아요도 함께 삭제한다.

### 범위 밖 — 도입 시 이 결정들을 다시 본다
- 외부 결제(PG)가 없다. 재고·포인트·주문을 한 트랜잭션으로 묶어 롤백하므로 보상 트랜잭션을 구현하지 않는다. PG 가 들어오면 확정이 두 사건으로 쪼개지고 환불 대기·재시도·멱등키가 필요해진다.
- 배송·출고가 없다. 그래서 취소를 확정 전·후 두 경우로만 다룬다. 출고가 생기면 반송·반품으로 분화하고 주문 상태가 다축이 된다.
- 주문 조회·히스토리가 없다. 다만 확정 시 단가를 저장하는 것은 위 규칙대로 지금부터 지킨다.
