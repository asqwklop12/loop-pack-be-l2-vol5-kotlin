# 아웃박스 운영 경계와 한계

상태를 어떻게 구분하고, 밀렸을 때 무엇을 보고, 어디까지 보장하지 않는지 정리한다.
"관찰"은 로컬 1회 실행의 값이고, "코드"는 코드를 읽어 판단했을 뿐 돌려 보지 않은 내용이다.

## 상태 구분

| 상태 | 뜻 | 기록하는 곳 | 기록하는 쪽 |
|---|---|---|---|
| `PENDING` | 확정은 커밋됐고 브로커 ack 를 아직 기록하지 못했다 | `outbox_event.status` | `commerce-api` (결제 성공과 같은 TX) |
| `SENT` | 브로커가 받았다고 답했다 | `outbox_event.status` | `commerce-api` 또는 `commerce-relay` |
| 소비 완료 | 컨슈머가 구매 활동을 반영했다 | `processed_order_confirmation` | `commerce-streamer` |

`SENT` 는 소비 완료가 아니다. 컨슈머를 띄우지 않으면 `SENT` 인 채로 소비 기록이 없다.
로컬 DB 에 실제로 그런 행이 남아 있다 (2026-11-06 조회: `SENT` 24,568 중 소비 기록 없음 3,481).

`PENDING` 도 미발행과 같은 뜻은 아니다. 브로커에는 들어갔는데 ack 나 `SENT` 기록만 실패한 행도
`PENDING` 이다. `outbox-broker-down.md` 의 재발행 2건이 이 경우다.

```sql
select e.status, p.event_id is not null as consumed, count(*)
from outbox_event e
left join processed_order_confirmation p on p.event_id = e.event_id
group by 1, 2;
```

## 실패와 backlog

| 상황 | 드러나는 곳 | 행 |
|---|---|---|
| api 직접 전송 실패 | 로그 `주문 이벤트 발행 실패` | `PENDING` 유지 |
| 릴레이 전송 실패 | 로그 `아웃박스 릴레이 실패. 다음 주기에 다시 보낸다` | `PENDING` 유지 |
| api 의 `markSent` 실패 | **드러나지 않는다** (코드: 콜백 예외를 받는 쪽이 없다) | `PENDING` 유지 |

backlog 를 알려 주는 메트릭은 없다. 직접 조회한다.

```sql
select count(*), min(created_at)
from outbox_event
where status = 'PENDING';
```

행 수만으로는 원인을 가르지 못한다. 브로커 장애와 `SENT` 기록 지연이 같은 모양으로 보인다.
`sent_at` 이 없어 생성부터 `SENT` 까지 걸린 시간도 남지 않는다.

## 재개

1. 브로커를 복구한다. 확정은 브로커 상태와 상관없이 계속 받는다.
2. 릴레이의 다음 주기를 기다린다. 기본은 30분이고 `RELAY_CRON` 으로 바꾼다.
3. 위 조회로 `PENDING` 이 줄었는지, 로그에 실패가 없는지 본다.

릴레이는 `PENDING` 을 id 순으로 500건씩 끝까지 읽으므로 별도의 재개 지점이 없다.
관찰: 브로커 셋을 내려 쌓인 16,115건이 릴레이 1회로 전부 `SENT` 가 됐다 (`outbox-broker-down.md`).

## 미발행 사실의 보존

코드 어디에도 아웃박스 행을 지우는 경로가 없다. 전송에 계속 실패해도 행은 `PENDING` 으로 남는다.

W6 처럼 아웃박스 이전에 빠진 사건은 행 자체가 없어 릴레이가 찾지 못한다. 이때는 SQL 로 백필한다
(`w6-missing-recovery.md`).

## 한계

### 단일 릴레이

- 인스턴스 하나를 전제한다. 조회에 잠금이 없어, 둘을 띄우면 같은 행을 함께 보낸다 (코드).
- 릴레이가 죽어 있는 동안은 아무도 다시 보내지 않는다. 행은 남고 다음 기동 때 나간다 (코드).

### 중복

- 릴레이의 조회에는 생성 시각 유예가 없다. api 가 막 보낸 행이 아직 `PENDING` 이면 릴레이가 한 번 더 보낸다 (코드).
- 브로커에 기록된 뒤 ack 를 잃어도 재발행된다. 관찰: 2건 (`outbox-broker-down.md`).
- 이 중복을 막는 것은 아웃박스가 아니라 컨슈머의 eventId 중복 거르기다.
- 프로세스가 ack 직후 `SENT` 를 쓰기 전에 죽는 경우는 재지 않았다. 같은 재발행 경로로 예상한다.

### 보존

- `SENT` 행도 지우지 않는다. 테이블은 확정 건수만큼 계속 커진다. 보존 기간과 정리 작업이 없다.
- 토픽 보존 기간은 따로 정하지 않았다. 소비가 그보다 오래 멈추면, 이미 `SENT` 인 행은 릴레이가 다시 보내지 않으므로 수동 복구가 필요하다 (코드).

### 재시도

- 횟수 제한, 백오프, 격리가 없다. 계속 실패하는 행은 주기마다 다시 시도하며 로그만 남긴다.
- 실패가 계속돼도 알림이 없다. 컨슈머 쪽 DLT 알림은 있지만 전송 쪽에는 없다.
- 주기가 30분이라 복구가 그만큼 늦을 수 있다.
- 재발행은 뒤늦게 나가므로 같은 키 안의 순서를 보장하지 않는다. 지금은 주문당 확정 이벤트가 하나라 영향이 없다.

### `SENT` 기록 지연

`markSent` 는 현재 `whenComplete` 로 Sender 스레드에서 돈다. DB 가 느려지면 전송도 함께 느려질 것으로 보며, 재지 않았다 (코드).

이전의 `whenCompleteAsync` 버전(`a21914f`)은 건당 4.4초로 늦춰 봤다. 유입 초당 5건, commonPool 11스레드 조건이다.

| 항목 | 관찰 |
|---|---|
| 전송 | 멈추지 않았다. 토픽 증가량이 행 수를 따라갔다 |
| `PENDING` | 최대 551건 |
| 지연을 푼 뒤 | 8건이 로그 없이 `PENDING` 으로 남았다 |
| 부수 효과 | 첫 실행에서 약 1분간 DB 커넥션 타임아웃. 원인은 밝히지 못했고, 재실행에서는 재현되지 않았다 |

## 검증하지 않은 것

- 릴레이 인스턴스를 둘 띄운 경우
- 브로커가 `delivery.timeout.ms` 안에 돌아오는 경우
- api 프로세스 강제 종료
