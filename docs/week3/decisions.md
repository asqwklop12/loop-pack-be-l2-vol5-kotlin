# 동시성 결정

### 확정 순서

- 되돌리기 싼 것부터 한다. `재고 감소 → 포인트 차감 → CONFIRMED` 다.
- `DRAFT` 검사는 **아무것도 바꾸기 전에** 한다. 그래서 `Order.requireDraft` 를 `confirm` 에서 따로 꺼내 부른다. 롤백되므로 결과는 같지만 흐름도의 순서와 달랐다.

### 선택 기준

- **낙관락** — 시스템으로서 동작이 가능해야 한다면 낙관락을 쓴다. DB 에 칼럼을 하나 더해 제어하는 방식이라, 따로 통제하지 않아도 시스템이 알아서 돌아가는 쪽에 가깝다고 봤다.
- **비관락** — 어떤 문제를 통제하고 싶을 때 쓴다. 통제하면 대기가 생길 수밖에 없고, 그 대기를 감당할 수 있어야 비관락을 고른다.
- **재시도는 넣지 않는다.** 실패 처리가 한 겹 더 생겨 오히려 꼬인다.

### 경합별 결과

"같은 행을 건드렸는가" 로는 갈리지 않는다. **둘 다 성립하는 요청인가**로 본다.

|                                     | 둘 다 성립하나         | 지금 결과                         |
| ----------------------------------- | ---------------------- | --------------------------------- |
| 같은 주문을 두 번 확정              | 안 됨                  | 하나는 `409`                      |
| 한 상품을 여러 주문이 확정          | 재고가 충분하면 **됨** | 하나는 `409` — 거짓 거절          |
| 재고 변경과 주문 확정               | **됨**                 | 하나는 `409` — 거짓 거절          |
| 취소와 다른 주문의 확정 (같은 상품) | **됨**                 | 하나는 `409` — 거짓 거절          |
| 한 사용자가 여러 주문을 확정        | 잔액이 충분하면 **됨** | 둘 다 성공. 모자라면 하나는 `400` |
| 충전과 결제                         | **됨**                 | 둘 다 성공                        |

재고 쪽 거짓 거절 셋은 **낙관락을 고르면서 받아들인 대가**다. 경합이 드물다고 봤다.

### 주문 — 낙관락

- **주문 확정은 하나만 성공해도 된다.** 따닥이면 둘 중 하나가 거절돼도 문제가 없다. 그래서 낙관락으로 간다.
- `Order` 에 `@Version` 을 둔다. `DRAFT → CONFIRMED` 는 한 번만 일어나야 한다.
- `requireDraft` 의 검사와 저장 사이에 다른 트랜잭션이 끼어들 수 있었다. 둘 다 `DRAFT` 를 보고 통과해 한 주문이 두 번 결제됐다.
- 취소에도 같이 걸린다. **둘 다 막아야 한다.** 확정이 두 번이면 돈이 두 번 나가고, 취소가 두 번이면 없던 돈이 생긴다. 손실의 방향만 다르다.

### 재고 — 낙관락

- 재고 차감은 **시스템의 한 축**이다. 통제 지점이 아니라 자연스럽게 흘러가야 하는 단계라고 봤다.
- 재고와 포인트가 **한 API 안에** 있다. 재고까지 비관락으로 잡으면 한 요청이 두 번 줄을 서게 되어 **확정의 락 대기가 길어진다.**
- **대가**: 거짓 거절이 셋 생긴다(위 표). 관리자 재고 변경, 같은 상품을 담은 다른 주문의 확정, 그 상품의 주문 취소(`restoreStock` 도 `Product` 의 `@Version` 을 탄다)가 서로 겹치면 한쪽이 `409` 를 받는다. 다시 누르면 되고 경합이 드물다고 보아 받아들인다.

### 포인트 — 비관락

- 처음에는 **재고와 같은 이유로 낙관락**이었다.
- 바꾼 이유는 **충전과 차감이 동시에 일어나면 둘 중 하나가 실패할 수 있다**는 것이다. 둘 다 성립하는 요청인데 거절되는 것이라, 이건 통제하고 싶었다. 대기를 감당하더라도 줄을 세우는 쪽을 골랐다.
- `10,000 + 2,000 - 7,000 = 5,000` 으로 잔액이 맞는다. 낙관락일 때는 같은 행을 건드렸다는 이유만으로 나중 쪽이 `409` 를 받아 **정상 동작이 막혔다.**
- **잔액을 바꾸는 경로만** 잠근다. `getBalance` 는 읽기만 하므로 잠그지 않는다. `refund` 는 `charge` 를 타므로 함께 적용된다.
- **잔액 행을 먼저 만든 뒤에 잠근다.** 잠금 조회는 행이 있을 때만 줄을 세운다. 없으면 두 요청 모두 새로 만들어 유니크 제약에 부딪히고, InnoDB 에서는 갭 락 때문에 데드락이 난다. 첫 충전이 겹치면 하나가 통째로 사라졌다.
- 잔액 초과 결제의 응답이 바뀐다. **낙관락을 걸었던 중간 상태**에서는 진 쪽이 버전 충돌로 `409` 를 받았는데, 비관락에서는 기다린 쪽이 갱신된 잔액을 읽고 `400` 잔액 부족으로 막힌다. 사실에 가깝다.

### 예외 응답

- `ObjectOptimisticLockingFailureException` 은 `409` 다. 핸들러가 없으면 `Throwable` 로 떨어져 `500` 이 나간다. 서버 오류가 아니라 **이미 처리된 요청을 다시 보낸 것과 같은 상황**이다.
- 메시지는 구체적으로 쓸 수 없다. 같은 예외가 확정·취소 양쪽에서 올라와 어느 쪽인지 모른다.

### 범위 밖

- **멱등키** — 주문 생성 따닥은 막지 않는다. 생성이 아무것도 차감하지 않아 피해가 작고, 같은 내용의 주문서 둘이 비정상이라고 단정할 수 없다. 막으려면 클라이언트가 키를 보내야 한다.
- **DRAFT 수명** — 확정하지 않은 주문서를 치우는 주체가 없다.
- **포인트 원장** — 잔액 행을 갱신하는 대신 내역을 추가하면 경쟁 자체가 사라진다. 대신 잔액을 읽을 때마다 합계를 내야 하고, 잔액이 음수가 되지 않는다는 것은 따로 지켜야 한다.
