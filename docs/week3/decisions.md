# 동시성 결정 — 3주차

2주차 결정은 `../week2/decisions.md`, 흐름도는 `../week2/usecase.md` 에 있다.

### 차감 시점
- 주문 생성은 **주문서만 만든다.** 재고도 포인트도 건드리지 않는다. 유스케이스 23번이다.
- 재고 차감은 **주문 확정**에서 포인트 결제와 한 트랜잭션으로 일어난다. 유스케이스 24번이다.
- 생성에 남긴 상품 조회는 **상품 확인과 단가 고정**을 위한 것이다. 주문 시점의 가격은 나중에
  알아낼 수 없으므로 여기서 복사해 두어야 한다.
- 확정 전 취소는 재고를 건드리지 않는다. 잡은 적이 없는 재고를 복원하면 없던 재고가 늘어난다.
- 상품 존재·판매중지는 **확정에서 다시 확인한다.** 주문서를 만든 뒤 상품이 내려갈 수 있다.

### 확정 순서
- 되돌리기 싼 것부터 한다. `재고 감소 → 포인트 차감 → CONFIRMED` 다.
- `DRAFT` 검사는 **아무것도 바꾸기 전에** 한다. 그래서 `Order.requireDraft` 를 `confirm` 에서
  따로 꺼내 부른다. 롤백되므로 결과는 같지만 흐름도의 순서와 달랐다.

### 락 — 무엇을 막고 무엇을 막지 않나
경쟁을 **막아야 하는 것**과 **막으면 안 되는 것**으로 가른다. 같은 행을 건드렸다는 사실만으로는
갈리지 않는다.

| | 둘 다 성공해도 되나 | 결과 |
| --- | --- | --- |
| 같은 주문을 두 번 확정 | 안 됨 | 하나는 `409` |
| 한 상품을 여러 주문이 확정 | 안 됨 | 하나는 `409` |
| 한 사용자가 여러 주문을 확정 | 안 됨 | 하나는 `400` 잔액 부족 |
| **충전과 결제** | **됨** | 둘 다 성공 |
| **재고 변경과 주문 확정** | **됨** | 하나는 `409`. 받아들인다 |

### 주문 — 낙관락
- `Order` 에 `@Version` 을 둔다. `DRAFT → CONFIRMED` 는 한 번만 일어나야 한다.
- `requireDraft` 의 검사와 저장 사이에 다른 트랜잭션이 끼어들 수 있었다. 둘 다 `DRAFT` 를 보고
  통과해 한 주문이 두 번 결제됐다.
- 취소에도 같이 걸린다. **취소 따닥이 확정 따닥보다 나쁘다.** 확정이 두 번이면 돈이 두 번
  나가지만 취소가 두 번이면 없던 돈이 생긴다.
- 재시도는 넣지 않는다. 다시 읽어도 `CONFIRMED` 라 또 막히므로 의미가 없다.

### 재고 — 낙관락
- 재고 차감은 통제 지점이 아니라 **주문이 돌아가기 위한 한 단계**다. 사람이 누구에게 팔지
  정하는 것이 아니라 되는지 안 되는지 판정하고 끝난다.
- 상품이 분산되어 있어 같은 행에 몰리는 구조가 아니다. 한정 수량·타임세일 같은 것이 없다.
- 비관락이면 여러 품목을 **어떤 순서로 잠그나**가 따라온다. 두 주문이 상품 A·B 를 반대 순서로
  잠그면 데드락이다. 낙관락은 그 문제가 없다.
- **대가**: 관리자 재고 변경이 주문 확정과 겹치면 한쪽이 거절된다. 둘 다 성립하는 요청이므로
  거짓 거절이다. 관리자가 가끔 하는 일이고 다시 누르면 되므로 받아들인다.

### 포인트 — 비관락
- 충전과 결제는 같은 잔액 행을 다투지만 **둘 다 성립한다.** `10,000 + 2,000 - 7,000 = 5,000`
  으로 잔액이 맞는다. 낙관락은 같은 행을 건드렸다는 이유만으로 나중 쪽을 떨어뜨려
  **정상 동작을 막았다.**
- 재시도로도 풀 수 있지만 넣지 않기로 했으므로 줄을 세운다.
- 포인트 행은 한 사용자의 것이라 몰리지 않고, 여러 행을 잠그는 것이 아니라 락 순서를 맞출
  일도 없다.
- **잔액을 바꾸는 경로만** 잠근다. `getBalance` 는 읽기만 하므로 잠그지 않는다. `refund` 는
  `charge` 를 타므로 함께 적용된다.
- 잔액 초과 결제가 `409` 에서 `400` 으로 바뀐다. 기다린 쪽이 갱신된 잔액을 읽고 잔액 부족으로
  막히기 때문이다. "다른 요청이 먼저 처리되었습니다" 보다 사실에 가깝다.

### 예외 응답
- `ObjectOptimisticLockingFailureException` 은 `409` 다. 핸들러가 없으면 `Throwable` 로 떨어져
  `500` 이 나간다. 서버 오류가 아니라 **이미 처리된 요청을 다시 보낸 것과 같은 상황**이다.
- 메시지는 구체적으로 쓸 수 없다. 같은 예외가 확정·취소 양쪽에서 올라와 어느 쪽인지 모른다.

### 범위 밖
- **멱등키** — 주문 생성 따닥은 막지 않는다. 생성이 아무것도 차감하지 않아 피해가 작고, 같은
  내용의 주문서 둘이 비정상이라고 단정할 수 없다. 막으려면 클라이언트가 키를 보내야 한다.
- **DRAFT 수명** — 확정하지 않은 주문서를 치우는 주체가 없다.
- **포인트 원장** — 잔액 행을 갱신하는 대신 내역을 추가하면 경쟁 자체가 사라진다. 대신 잔액을
  읽을 때마다 합계를 내야 하고, 잔액이 음수가 되지 않는다는 것은 따로 지켜야 한다.
