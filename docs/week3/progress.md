## 1. 재고 차감을 생성에서 확정으로 옮김

명세가 "주문 생성은 DRAFT 를 저장하고 차감하지 않습니다. 기존 `POST /orders/{id}/confirm`
의 최초 확정을 개선합니다" 였다. **2주차에 직접 정한 설계를 뒤집는 요구**였다.

### 흐름도부터

`usecase.md` 1번은 `주문서 제작 → 재고 차감 → 주문 확정 → 결제` 순이었다. 그림이 말하는 건
**단계의 순서**이고 어느 요청이 어디까지 맡는지는 안 그려져 있었다. 그래서 **자르는 위치만**
옮기면 그림은 그대로였다.

```
명세대로   생성 = 주문 시작 ~ 주문서 제작      확정 = 재고 차감 ~ 주문 완료
그 전      생성 = 주문 시작 ~ 재고 차감        확정 = 주문 확정 ~ 주문 완료
```

23번(주문 생성)과 24번(주문 확정)을 새로 그렸다. 1번은 손대지 않았다.

2번(확정 전 취소)에서 **`재고 복원` 노드를 뺐다.** 확정 전에는 잡은 재고가 없어 복원할 것이
없다. 그대로 두면 그림이 거짓이 된다.

### 24번에 트랜잭션 묶음을 그렸다

`재고 감소 · 포인트 차감 · CONFIRMED` 를 `subgraph` 로 묶고 라벨에 "전부 반영되거나 전부
취소된다" 를 넣었다. 되돌림을 **단계로 그리지 않은 이유**가 이것이다. 묶음이 설명하므로
`잔액 부족 → 재고 복원` 같은 노드가 필요 없다.

주문 조회와 본인·DRAFT 검사는 **묶음 밖**이다. 아무것도 바꾸기 전에 끝나 되돌릴 것이 없다.

### 코드

| 바꾼 것 | |
| --- | --- |
| `create` | `decreaseStock` 제거. `getSellable` 은 남김 |
| `confirm` | 품목마다 `getSellable` → `decreaseStock`, 그다음 결제 |
| `cancel` | 재고 복원을 **확정된 주문만**으로 좁힘 |

`getSellable` 을 생성에 남긴 이유가 둘이다. 그림 1번의 거절 사유가 `없는 상품 / 삭제된 상품`
이라 생성에서 상품을 봐야 하고, **단가를 여기서 고정**해야 한다. 주문 시점의 가격은 나중에
알아낼 수 없다.

`Order.requireDraft` 를 따로 뺐다. 전에는 `confirm()` 안에서만 검사해 **재고를 줄이고 결제까지
한 뒤에** 상태를 봤다. 롤백되니 결과는 같지만 그림 순서와 달랐다.

### 뒤집힌 테스트

| 전 | 후 |
| --- | --- |
| 생성 시 재고가 차감된다 | 재고는 그대로다 |
| 생성 시 재고 부족이면 400 | 주문서는 만들어진다 |
| 확정 전 취소하면 재고가 복원된다 | 재고를 건드리지 않는다 |
| 잔액 부족 시 재고 4 | 재고 5 (복구됨) |

새로 넣은 것은 확정 재고 부족(400, 포인트 불변), 확정 시 상품 삭제·판매중지(404).

픽스처 하나를 고쳤다. 20절 가드 테스트의 상품이 `stock = 2` 였는데, 생성이 재고를 안 줄이니
삭제가 `CONFLICT` 로 막혀 셋업이 성립하지 않았다. `stock = 0` 으로 바꿨다.

## 2. 여러 품목 롤백

통합 테스트의 주문이 **전부 품목 하나**였다. 품목이 하나면 되돌릴 앞 단계가 없어, 앞 품목이
함께 되돌아가는지를 한 번도 밟아 보지 않았다.

```
품목 1개   재고 차감 → [실패]            되돌릴 앞 단계 없음
품목 2개   A 차감 → B 차감 → [실패]      A 가 되돌아가는지가 걸림
```

**실패를 재고가 모두 줄어든 뒤 결제 단계에서 터뜨렸다.** 품목 하나를 재고 부족으로 만들면
그 품목이 먼저 처리될 수 있어 앞 품목이 쓰이기도 전에 끝난다. 2주차 19절에서 겪은 함정이다.

`decreaseStock` 에 `REQUIRES_NEW` 를 붙여 품목마다 따로 커밋하게 만들고 **3건이 실패하는 것을
확인**한 뒤 되돌렸다.

## 3. 동시성 구멍 셋

막는 자리가 달라 한 번에 묶이지 않는다. 각각 테스트를 썼고 셋 다 RED 였다.

| | 다투는 쪽 | 겹치는 행 |
| --- | --- | --- |
| ① | 같은 주문에 요청 둘 | `orders` |
| ② | 다른 주문 둘, 같은 상품 | `product` |
| ③ | 다른 주문 둘, 같은 사용자 | `point_balance` |

실패 이유가 셋 다 `성공 2, 기대 1` 이었다.

**재고·잔액 단정은 통과했다.** 재고 0, 잔액 3,000 으로 겉보기엔 멀쩡하다. 둘이 같은 값을 읽고
같은 값을 써서 숫자는 정상 범위에 있다. 어긋난 건 **팔린 개수와 줄어든 재고가 안 맞는다**는
쪽이라, 성공 건수를 세지 않으면 안 잡힌다.

모든 스레드를 `CountDownLatch` 로 대기시켰다가 한 신호에 푼다. 순차로 돌면 경쟁이 안 일어나
그냥 통과한다.

## 4. 낙관락과 비관락 — 어디에 무엇을

### 가른 기준

처음에는 "시스템으로 돌아가야 하는 건 낙관, 통제하고 싶으면 비관" 으로 갈랐다. 그런데
**재고도 통제 대상이 아니라 시스템의 한 단계**다. 사람이 누구에게 팔지 정하는 게 아니라
되는지 안 되는지 판정하고 끝난다. 그래서 그 축으로는 안 갈렸다.

쓸모 있었던 축은 **"둘 다 성공해도 되는가"** 였다.

```
안 됨   ① 같은 주문 두 번 확정 · ② 재고 1개를 둘이 · ③ 잔액 초과
됨      충전 + 결제 · 재고 변경 + 주문 확정
```

낙관락은 **같은 행을 건드렸다는 사실만으로** 떨어뜨린다. 그래서 "둘 다 성공해도 되는" 조합이
있는 곳에서는 **거짓 거절**이 난다.

### DB 를 믿느냐

```
낙관락   그냥 저장한다. 아무 요청도 안 함. "어긋나면 DB 가 알려주겠지"  → 맡김
비관락   FOR UPDATE 로 먼저 잠가 달라고 명시적으로 부탁한다            → 시킴
```

코드에도 그대로 드러난다. 낙관락은 `@Version` 한 줄이고 쿼리에 쓴 것이 없다 — Hibernate 가
`where version = ?` 를 붙인다. 비관락은 직접 `FOR UPDATE` 를 적어 넣는다.

### 결정

| | 선택 | 이유 |
| --- | --- | --- |
| 주문 | 낙관락 | 재시도해도 `CONFIRMED` 라 또 막힌다. 바로 `409` |
| 재고 | 낙관락 | 상품이 분산됨. 여러 품목 락 순서 문제가 없음 |
| 포인트 | **비관락** | 충전과 결제가 **둘 다 성공해야** 한다 |

재시도는 넣지 않기로 했다. 포인트는 재시도로도 풀리지만 줄을 세우는 쪽으로 갔다.

### 실제 SQL 확인

체크리스트가 "선택한 제어가 실제 호출·SQL 에 적용되고" 를 요구해 로그로 확인했다.

```sql
select ... from point_balance where user_id=? for update
update product set ... , version=? where id=? and version=?
update orders  set ... , version=? where id=? and version=?
```

**우회 경로도 없다.** `@Modifying` · `@Query` · 네이티브 쿼리가 하나도 없고, `Product` 와
`PointBalance` 를 바꾸는 모든 경로가 `save()` 를 탄다. 엔티티 레벨 `@Version` 이라 브랜드
삭제의 `suspendAllByBrand`, `changeStock`, `restoreStock`, `charge`/`refund` 가 전부 적용된다.

### 낙관락이 잡아낸 테스트 버그

2주차 20절 가드 테스트가 깨졌다. **확정 전에 읽어 둔 인스턴스로 저장**하고 있었다.

```kotlin
orderService.confirm(...)                       // 재고가 줄어 version 올라감
productJpaRepository.save(product.apply {...})  // 낡은 인스턴스 → 충돌
```

낙관락이 "낡은 값으로 덮어쓰기" 를 잡은 것이라 테스트가 틀렸다. 단정은 그대로 두고 저장
직전에 다시 읽게 했다.

## 5. 거짓 거절 — 충전과 결제

명세에 `잔액 10,000 에서 2,000 충전과 7,000 결제를 함께 실행 → 두 요청 성공 · 기술 오류 0 ·
최종 5,000` 이 있었다. **낙관락을 넣은 직후 이 항목이 깨졌다.**

```
A(충전) 10,000 읽음 → 12,000 저장 ✓  version 1→2
B(결제) 10,000 읽음 →  3,000 저장 ✗  version 이 1 이 아님
```

앞의 ①②③과 **성격이 반대**다. 저 셋은 막아야 맞고 이건 둘 다 되어야 맞다. 락이 **과하게
막는지**를 보는 자리다.

포인트만 비관락으로 바꿨다. `PointBalance` 의 `@Version` 을 빼고 `findByUserIdForUpdate` 를
더했다.

곁다리로 ③의 응답이 바뀌었다.

```
낙관락   409 "다른 요청이 먼저 처리되었습니다"
비관락   400 "잔액이 부족합니다"        ← 기다린 쪽이 갱신된 잔액을 읽는다
```

**사실에 가까운 쪽이 되었다.**

같은 모양이 하나 더 있다 — **재고 변경과 주문 확정**이다. `5 + 10 - 2 = 13` 으로 둘 다
성립하는데 낙관락이 하나를 떨어뜨린다. 관리자가 가끔 하는 일이고 다시 누르면 되므로
받아들이기로 했다.

## 6. 음성 대조군

갱신 유실이 무엇인지를 **돌아가는 코드로** 남겼다. 깨진 결과를 기대값으로 적어 통과하는
테스트로 만든다. 의도적인 실패를 방치하지 않는다.

```
커밋된 재고 5
  ├─ 독립된 트랜잭션 2개가 잠금 없는 SELECT 로 읽음
  ├─ 읽기 장벽 — 둘 다 5를 읽은 뒤에야 쓰기 허용
  ├─ 조건도 버전도 없이 상수 4 를 저장
  └─ 성공 2 · 최종 재고 4 · 2 + 4 ≠ 5
```

**파일을 나눴다.** 읽기 장벽은 대조군에만 있다. 실제 검증에 넣으면 진짜 동작이 아니라
꾸며낸 상황을 보게 된다.

**JDBC 로 직접 쓴다.** `Product` 에 `@Version` 이 있어 엔티티로 저장하면 Hibernate 가
`where version = ?` 를 붙이고, 그러면 갱신 유실이 재현되지 않는다.

재현이 성립했는지부터 단정한다 — 제한 시간 안에 끝났는지, 스레드가 정리됐는지, 기술 오류가
없는지, 둘이 같은 값을 읽었는지. **시간 초과나 SQL 오류로 끝난 것은 갱신 유실이 아니다.**

## 7. 집계를 세 갈래로 가르고 대기를 정리

### 실패를 한 덩어리로 세고 있었다

```kotlin
catch (e: Throwable) { failures.add(e) }
return count - failures.size        // 성공 수만 나온다
```

그래서 **진 쪽이 무슨 답을 받았는지 몰랐다.** 성격이 완전히 다른 둘이 섞인다.

| 갈래 | 예 | 뜻 |
| --- | --- | --- |
| 업무 거절 | 재고 부족 · 잔액 부족 · 이미 확정됨 | 규칙대로 막힌 **정상 동작** |
| 기술 오류 | 낙관락 충돌 · 타임아웃 · SQL 오류 | 경쟁 때문에 **못 한 것** |

`CoreException` 만 따로 잡아 갈랐다. 도메인이 던지는 거절은 전부 그 타입이라 경계가 그대로 맞는다.

### 결정적인 칸만 못 박았다

| 테스트 | 단정 |
| --- | --- |
| ③ 잔액 초과 | 성공 1, **업무 거절 1 · 기술 오류 0** |
| ⑥ 충전 + 결제 | 성공 2, **기술 오류 0 · 업무 거절 0** |
| ① ② ④ ⑤ | 성공 1, **막힘 1** (갈래는 가르지 않음) |

①②④⑤는 낙관락이라 **진 쪽이 어느 갈래로 막힐지가 경쟁 시점에 따라 갈린다.** 정말 겹치면
낙관락 충돌이고, 아슬아슬하게 어긋나면 갱신된 값을 읽어 업무 거절이 된다. 둘 다 맞는
결과라 합으로만 단정했다. 한쪽으로 못 박으면 간헐적으로 깨진다.

③⑥은 비관락이라 **결정적이다.** 기다린 쪽이 반드시 갱신된 값을 읽으니 충돌이 날 수 없다.
그래서 `기술 오류 0` 을 못 박았고, 여기가 **재고(낙관)와 포인트(비관)의 선택 차이가 테스트에
드러나는 자리**다.

### 멈춘 작업이 성공으로 세어지고 있었다

```kotlin
done.await(10, TimeUnit.SECONDS)   // 반환값을 버렸다
pool.shutdown()                     // 끝날 때까지 기다리지 않는다
```

스레드가 멈추면 10초 뒤 그냥 넘어가고, 그 스레드는 `failures` 에 아무것도 안 넣었으니
**성공으로 집계됐다.** 포인트에 비관락을 넣어 대기가 실제로 생기는 구조가 된 참이었다.

`await` 결과와 `awaitTermination` 을 **집계 전에 단정**하도록 고쳤다.

한 작업을 12초 멈추게 해서 실제로 잡히는지 확인했다.

```
[모든 작업이 제한 시간 안에 끝난다] Expecting value to be true but was false
```
