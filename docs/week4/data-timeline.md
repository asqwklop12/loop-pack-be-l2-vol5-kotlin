# 측정용 데이터 — 세 시점

4주차는 조회 성능을 다룬다. 성능을 재려면 데이터가 있어야 하고, 그 데이터가
**실무와 다르면 측정 결과도 다르게** 나온다. 세 시점을 만든 기록이다.

---

## 1. 왜 세 시점인가

실무에서는 "오 여기가 느려"라는 신호가 먼저 오고 그걸 쫓아간다. 실습에는 그 신호가 없다.
대신 **같은 쿼리를 다른 시점의 데이터에 돌려서** 무엇이 달라지는지 본다.

| | 질문 |
| --- | --- |
| day1 | 지금 이 데이터에서 어디가 비싼가 |
| day2 | 6개월 뒤 데이터가 1.5배가 되면 그 비용이 어떻게 변하나 |
| day3 | 신규 브랜드가 들어와 **인기 순위가 뒤집히면** 무엇이 깨지나 |

day3 가 중요하다. day1·day2 는 선점 효과만 있어 "좋아요 많은 상품 = 오래된 상품" 이었다.
day3 에서 그 상관이 끊긴다.

## 2. 구성

컨테이너를 나눈다. 같은 MySQL 안에 스키마만 다르게 두면 버퍼 풀(128MB)을 서로 밀어내
"인덱스 효과" 와 "캐시 경합" 이 섞인다.

| | 컨테이너 | 포트 | 기준 시각 | 버퍼 풀 |
| --- | --- | --- | --- | --- |
| day1 | `docker-mysql-1` | 3306 | 2026-10-14 | 128MB |
| day2 | `mysql-day2` | 3307 | 2027-04-14 | 128MB |
| day3 | `mysql-day3` | 3308 | 2027-10-14 | 128MB |

스키마 이름이 셋 다 `loopers` 다. **같은 SQL 이 포트만 바꿔 돈다.**

```bash
# 접속
docker compose -f docker/infra-compose.yml exec -T mysql mysql -uroot -proot loopers   # day1
docker exec -i mysql-day2 mysql -uroot -proot loopers                                  # day2
docker exec -i mysql-day3 mysql -uroot -proot loopers                                  # day3

# day2·day3 올리고 내리기 (프로젝트 이름 -p 를 반드시 준다)
docker compose -p loopers-day2 -f docker/timeline-compose.yml up -d
docker compose -p loopers-day2 -f docker/timeline-compose.yml down
```

## 3. 세 시점 비교

| | day1 | day2 | day3 |
| --- | --- | --- | --- |
| 브랜드 | 100 (살아있음 95) | 100 (95) | **110 (105)** |
| 상품 | 1,000,000 | 1,500,000 | 1,976,833 |
| 좋아요 | 1,985,744 | 4,006,479 | 6,216,485 |
| 좋아요 최대 | 5,672 | 9,688 | 13,035 |
| 좋아요 0개 상품 | 600,000 | 900,000 | 1,171,333 |
| 판매중지 | 13.58% | 18.58% | 18.28% |
| 삭제 | 5.05% | 8.03% | 8.52% |
| 목록 노출 | 82.09% | 74.82% | 74.69% |
| 품절 | 6.19% | 6.19% | 6.20% |
| 가격 값 종류 | 168,799 | 175,717 | 179,532 |
| 브랜드 선택도 | 0.29% ~ 18.00% | 0.26% ~ 16.37% | 0.24% ~ 15.06% |

day3 에서 판매중지 비율이 day2 보다 **내려간 것은 희석**이다. 절대 수는 278,700 → 361,365 로
늘었지만 신규 상품 477,000 개가 대부분 판매중이라 분모가 커졌다. 재고를 새로 들이는
성장기 카탈로그에서 실제로 일어나는 일이라 그대로 뒀다.

상품 id 가 유지된다. 재생성이 아니라 **복사 후 숙성**이라 day1 의 상품이 day2·day3 에도
같은 id 로 있다. 같은 상품을 세 시점에서 추적할 수 있다.

## 4. 넣은 상관관계

무작위 데이터는 모양만 맞고 관계가 없다. 실무 쿼리의 성능은 **관계**에 달려 있다.

| 필드 | 규칙 | 왜 |
| --- | --- | --- |
| `id` | `created_at` 오름차순 | `AUTO_INCREMENT` 는 현실에서 등록 순서와 같이 오른다 |
| `brand_id` | `u^3` 분포, 3,333 ~ 215,789개 | 큰 브랜드와 작은 브랜드. 균등하면 선택도가 한 값으로 고정된다 |
| `price` | 브랜드마다 고유 가격대 × 상품별 변동 | 브랜드는 가격 구간을 점유한다. `(brand_id, price)` 인덱스가 브랜드마다 다르게 동작한다 |
| `created_at` | 전체 기간에 고르게 | 시드는 브랜드 묶음마다 `NOW()` 라 1만개가 같은 값이었다 |
| `stock` | `u^2.4 × 400`, 품절 6.2% | 대부분 적고 일부가 많다 |
| `status` | 나이와 상관. 신상 5% → 2년 31% | 오래된 상품이 더 많이 내려간다 |
| `deleted_at` | 나이와 상관. 삭제 시점은 등록 이후 | |
| 좋아요 수 | 인기도 순위의 멱법칙, **천장 없음** | 중간값 0, 상위 소수가 수천 개 |
| 인기도 | 나이 × 브랜드 크기 × 가격(역) × 무작위 | 오래될수록, 큰 브랜드일수록, 쌀수록 조금 더 눌린다 |
| 좋아요 `created_at` | 상품 등록 이후 ~ 기준 시각 | |

### day3 의 사건 — 신규 브랜드 입주

브랜드 10개(id 101~110)가 2027-04 ~ 2027-10 사이에 들어왔고, 상품 126,833개를 올렸다.
인기도 점수에 **2.4배 가중**을 줬다. 어리지만 인기가 나이에 비해 좋다.

| | 상품 | 평균 좋아요 |
| --- | --- | --- |
| 기존 브랜드 | 1,850,000 | 6.79 |
| **신규 브랜드** | 126,833 | **16.32** |

좋아요 상위 15개 중 8개가 신규 브랜드다. 1위는 **나이 161일**짜리 상품(13,035개)으로,
726일 된 기존 1위(9,688개)를 넘었다.

이것이 측정에 주는 의미 — `likes_desc` 상위권과 등록 순서의 상관이 끊긴다.
`created_at` 인덱스로 `likes_desc` 를 대신 받칠 수 없고, 좋아요 수를 미리 계산해 두는 쪽
(캐시·비정규화)의 값이 올라간다.

### day3 좋아요 분포

계단이 아니라 곡선이다. 상위 32개가 2,000개 이상을 갖고 59%는 0개다.

## 5. 정합성

세 시점 모두 0 건이다.

| 검사 | day1 | day2 | day3 |
| --- | --- | --- | --- |
| `id` 가 `created_at` 역순인 쌍 | 0 | 0 | 0 |
| 중복 `(user_id, product_id)` | 0 | 0 | 0 |
| 좋아요가 상품보다 먼저 생김 | 0 | 0 | 0 |
| 삭제가 등록보다 먼저 | 0 | 0 | 0 |
| 상품이 브랜드 입주보다 먼저 | — | — | 0 |

`id` 범위도 셋 다 1 부터 빈틈없이 연속이다.

## 6. 재현 순서

```bash
# day1 — 3306 (기존 컨테이너)
mysql ... < docs/week4/seed-large.sql             # 브랜드 100 · 상품 100만 · 좋아요 100만
mysql ... < docs/week4/skew-distribution.sql      # 분포 교정 (균등 → 편중)
mysql ... < docs/week4/realistic-distribution.sql # 멱법칙 · 상관관계 · 시간순

# day2 — 3307
docker compose -p loopers-day2 -f docker/timeline-compose.yml up -d mysql-day2
mysqldump day1 | mysql day2                       # 스키마 + 데이터 복사
mysql ... < docs/week4/day2-aging.sql             # +6개월

# day3 — 3308
docker compose -p loopers-day2 -f docker/timeline-compose.yml up -d mysql-day3
mysqldump day2 | mysql day3
mysql ... < docs/week4/day3-aging.sql             # +12개월, 브랜드 입주

# 세 DB 각각
mysql ... < docs/week4/fix-id-ordering.sql        # id 순서 + 중복 제거
```

`skew-distribution.sql` 과 `realistic-distribution.sql` 은 전자가 후자에 흡수되는 관계가
아니라 순서대로 겹쳐 쓴다. `realistic-distribution.sql` 이 `brand_id` 편중과
`created_at` 분산을 전제로 한다.

## 7. 아직 실무와 다른 것

측정 결과에 함께 적어야 하는 한계다.

| | 무엇이 | 영향 |
| --- | --- | --- |
| 1 | **조회 분포가 없다.** 어느 행이 자주 읽히는지는 데이터에 담을 수 없다 | 캐시 적중률을 숫자로 말할 수 없다. 가정으로 명시해야 한다 |
| 2 | **주문·포인트가 0건.** `orders` · `order_line` · `point_balance` 전부 비어 있다 | `stock` 이 난수고 판매 이력과 무관하다. 인덱스가 주문 경로의 쓰기를 깎는 비용을 수치로 못 본다 |
| 3 | **요청 빈도가 없다.** 어느 API 가 많이 불리는지 모른다 | "시간 × 빈도" 의 둘째 항이 비어 있다 |
| 4 | **밀리초는 옮겨 쓸 수 없다.** 버퍼 풀 128MB 에 데이터 200MB 이상, 적중률 99.9% 인 따뜻한 캐시 | 환경을 건너가는 값은 **읽은 행 수**와 **비율**뿐이다 |
| 5 | **동시성이 안 보인다.** 단일 쿼리 측정으로는 커넥션 풀 대기도 락 경합도 드러나지 않는다 | 부하를 걸어야 나온다 |
| 6 | 상품명에 박힌 숫자가 `id` 와 맞지 않는다 | 원래도 의미 없는 값이다. 무해 |
| 7 | `uk_like_user_product` 가 없다 | 인덱스 구성을 직접 고르기 위해 지운 상태다. 정하고 나서 되살리며 공존 방법을 결정한다 |

2번은 이번 주차에 쓰지 않기로 했다.
