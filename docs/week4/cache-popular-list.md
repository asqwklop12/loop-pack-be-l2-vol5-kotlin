# 인기순 목록 캐싱

`likes_desc` 는 인덱스로 해결되지 않는 유일한 조회였다. 거기에 캐시를 걸었다.

---

## 1. 왜 이 경로인가

`likes_desc` 의 정렬 키는 `ORDER BY COUNT(product_like.id)` 다. **저장된 컬럼이 아니라
계산된 값**이라 미리 정렬해 둘 대상이 없다. 20개를 돌려주려고 판매 중인 상품 전부의
좋아요를 세고 전부 정렬한다. `LIMIT 20` 은 맨 마지막에 붙어 읽기를 줄여주지 않는다.

`latest` 와 `price_asc` 는 `created_at` · `price` 가 저장된 컬럼이므로 인덱스가 순서를
들고 있다. 그래서 캐시를 둘 이유가 없다 — `(brand_id, price)` 인덱스로 1,930ms → 1.7ms 가
됐다.

사용자별 필드도 없다. 응답 7필드(`id` `name` `price` `stock` `brandId` `brandName`
`likeCount`)가 누가 요청해도 같은 값이라, 캐시가 성립하는 조건을 통과한다.

## 2. 무엇을 담는가 — 정렬 결과만

담는 것은 **상품 id 의 순서**뿐이다. 상품 내용은 담지 않는다.

```
키    product:search:likes_desc:brand={id|all}:page={n}:size={m}
값    "1494431,1283183,1106296, ..."   (쉼표로 이은 id)
TTL   60초
```

| | |
| --- | --- |
| 재사용하는 것 | 좋아요 순위 (= 상품 id 의 순서) |
| 담지 않는 것 | 가격 · 재고 · 좋아요 수 — 매번 DB 에서 읽는다 |
| 제외한 사용자별 정보 | 없음. 지금 응답에 사용자별 필드가 없다 |

`stock` 을 담지 않은 이유가 핵심이다. 주문마다 바뀌는 값이라, 한 덩어리로 담으면
**가장 자주 바뀌는 필드가 덩어리 전체의 수명을 정한다.** id 순서만 담으면 지난 값이 되는
것은 순위 하나뿐이다.

## 3. 이 캐시를 틀리게 만드는 쓰기

`product` 를 바꾸는 경로는 일곱이지만, **이 캐시를 틀리게 만드는 것은 그중 일부**다.
담은 것이 좋아요 순서로 정렬된 id 목록뿐이기 때문이다. 둘을 섞으면 무효화 범위가
필요 이상으로 커진다.

지켜야 할 것이 둘이라 칸을 나눈다.

- **계약** — "목록에는 판매 중인 상품만 나온다"
- **순위 정확도** — "좋아요가 많은 순서가 맞다"

| 쓰기 경로 | 계약 | 순위 정확도 | 왜 |
| --- | --- | --- | --- |
| **좋아요 / 좋아요 취소** | 해당 없음 | **틀려진다** | 순위가 바뀌는데 캐시는 `put` 시점 값을 들고 있다 |
| 상품 삭제 | **지켜진다** | 해당 없음 | 읽을 때 `isSellable()` 로 걸러낸다 |
| 브랜드 삭제 → 판매중지 | **지켜진다** | 해당 없음 | 같음 |
| 관리자 가격 · 이름 수정 | 영향 없음 | 영향 없음 | 캐시에 없고 순위에도 안 쓰인다 |
| 관리자 재고 변경 | 영향 없음 | 영향 없음 | 같음 |
| 주문 확정 · 취소 (재고) | 영향 없음 | 영향 없음 | 같음 |
| 상품 생성 | 영향 없음 | 거의 없음 | 좋아요 0 이라 상위권에 못 든다. 전체가 20개 미만이면 든다 |

### 읽기 필터가 지키는 것은 계약이지 순위가 아니다

```kotlin
productRepository.findAllByIds(productIds)
    .filter { it.isSellable() }     // 존재 여부만 본다. 좋아요 수는 안 본다
```

"목록에 있으면 안 되는 상품" 은 빠지지만 **"이 자리에 있으면 안 되는 상품" 은 그대로
남는다.** 좋아요 5,672개였던 상품의 좋아요가 전부 취소돼도, 캐시가 살아 있는 동안은
1위에 그대로 있다.

### 그래서 무효화 대상은 사실상 하나다

좋아요뿐이다. 그런데 **가장 자주 일어나는 쓰기**이기도 하다. 누를 때마다 버리면
캐시가 거의 비어 있게 된다.

그래서 무효화 대신 **얼마나 지난 순위까지 보여줄지**를 정했다.

| | |
| --- | --- |
| 허용 신선도 | **60초** — 좋아요가 반영되기까지 최대 이만큼 늦는다 |
| 지키는 것 | 판매 중인 상품만 나온다 (지난 순위를 쓰더라도) |
| 포기한 것 | 순위의 즉시성 |

지금 이 값은 `ProductSearchRedisCache` 의 `TTL` 상수 하나로만 표현된다.
무효화를 넣게 되면 이 표가 바뀐다 — 좋아요 경로가 `evict` 를 부르게 되고,
허용 신선도가 "TTL 60초" 에서 "무효화 실패 시 최대 60초" 로 바뀐다.

## 4. 바꾼 파일

| | 책임 |
| --- | --- |
| `domain/product/ProductSearchCache.kt` (신규) | 포트 — 정렬 결과의 조회 · 저장 · 삭제 |
| `infrastructure/product/ProductSearchRedisCache.kt` (신규) | Redis 구현, 문자열 직렬화, 장애 시 우회 |
| `domain/product/ProductService.kt` (수정) | `search` 에서 `likes_desc` 만 캐시 경유 |

기존 `ProductRepository` → `ProductRepositoryImpl` 과 같은 패턴이다. 포트를 `domain` 에
두고 `infrastructure` 가 구현한다. ArchUnit 의 계층 규칙을 통과한다.

### 계약을 지키려고 넣은 것

캐시가 준 id 로 상품을 다시 읽을 때 **판매중지 · 삭제된 상품을 걸러낸다.**

지난 순위를 쓰더라도 "목록은 판매 중인 상품만" 은 지킨다. 그 대가로 한 페이지가 요청한
크기보다 짧아질 수 있다. 캐시에 담긴 순서를 그대로 믿고 내보내면, 30초 전에 내려간 상품이
목록에 다시 나타난다.

## 5. 결과 — 집계 정렬이 사라졌다

실제 API (`GET /api/v1/products?sort=likes_desc&size=20`), day1 데이터(상품 100만 ·
좋아요 198만), 단일 요청.

| | 시간 |
| --- | --- |
| 1회차 (miss) | **2,540 ms** |
| 2회차 (hit) | 245 ms |
| 3회차 | 241 ms |
| 4회차 | 252 ms |
| 5회차 | 245 ms |

**2,540 ms → 245 ms.** 10.4배.

### 히트 한 번의 쿼리 분해

`performance_schema` 를 비우고 히트 요청 하나만 보낸 결과다.

| 쿼리 | 호출 | 시간 | 읽은 행 | 보낸 행 |
| --- | --- | --- | --- | --- |
| `COUNT(id)` — totalCount | 1 | 221.9 ms | 1,000,000 | 1 |
| 좋아요 수 `IN (20개)` | 1 | 9.4 ms | 30,099 | 20 |
| 상품 `IN (20개)` | 1 | 1.4 ms | **20** | 20 |
| 브랜드 `IN (4개)` | 1 | 0.4 ms | 4 | 4 |

**집계 정렬이 목록에서 사라졌다.** 상품 조회가 `IN (20개)` 로 바뀌어 읽은 행이 20개다.
전에는 `product` 100만 + `product_like` 100만 = 200만 행을 읽고 정렬했다.

부하 아래서도 확인된다. 40 VU · 90초에서 요청 3,101건이 처리됐는데 **집계 쿼리는 41번만
돌았다** — 원본 호출이 3,101 → 41 로 줄었다.

## 6. 캐시 있음 / 없음 비교

같은 앱에 Redis 만 내렸다 올려 재측정했다. 코드는 그대로다 — Redis 가 죽으면
캐시가 없는 것처럼 동작하므로, 그 상태가 곧 "캐시 없음" 이다.

| | 캐시 없음 | 캐시 있음 | 차이 |
| --- | --- | --- | --- |
| 10 VU · 처리량 | 0.28 req/s | **32.1 req/s** | 116 배 |
| 10 VU · p95 | 33.2 s | **343 ms** | 97 배 |
| 40 VU · 처리량 | 1.91 req/s | **37.6 req/s** | 20 배 |
| 40 VU · 중앙값 | 21.36 s | **960 ms** | 22 배 |
| 40 VU · p95 | 22.77 s | **1.19 s** | 19 배 |

40 VU 무캐시는 300초 · 597건, 나머지는 20초 측정이다.

### 두 지표를 같이 봐야 하는 이유

**처리량**(초당 몇 건, 높을수록 좋다)과 **응답시간**(한 건이 얼마나 걸리나,
낮을수록 좋다)은 반대로 움직일 수 있다.

```
캐시 있음, 10 VU → 40 VU
  처리량    32.1 → 37.6 req/s   좋아짐
  응답시간   269 → 960 ms       나빠짐
```

동시에 더 많이 돌리니 총량은 늘었지만 한 사람이 기다리는 시간은 길어졌다.
한쪽만 보면 "개선" 과 "악화" 중 아무 결론이나 낼 수 있다. 캐시 비교는 다행히
둘이 같은 방향이다.

### 꼬리의 모양이 다르다

| | 중앙값 | p95 | p99 |
| --- | --- | --- | --- |
| 캐시 없음 (40 VU) | 21.36 s | 22.77 s | 23.26 s |
| 캐시 있음 (40 VU · TTL 만료) | 902 ms | 1.20 s | **21.17 s** |

무캐시는 **균일하게 느리다** — 중앙값과 p99 차이가 9% 다. 캐시는 **대부분 빠른데
가끔 똑같이 느리다** — p99 가 중앙값의 23배다. 평균만 보면 캐시 쪽이 압도적인데,
60초마다 한 번씩 일부 요청은 캐시가 없을 때와 같은 시간을 기다린다.

### 측정의 한계

10 VU 무캐시는 20초 동안 11건만 끝나 표본이 너무 작다. 40 VU 에서 처리량이
0.28 → 1.91 로 6.8배가 된 것은 동시성 효과가 아니라 그 표본 부족으로 보인다.
10 VU 도 길게 다시 재야 정확한 비교가 된다.

## 7. 장애 — Redis 를 실제로 내려봤다

### DB 우회는 된다

Redis 를 내린 상태에서 요청이 **200 으로 정상 응답**했고 데이터도 맞았다.
캐시 실패 자체의 비용은 거의 없다.

```
요청 전체   6.42 초
그중 DB     6.40 초   (집계 5,899ms + 좋아요 269ms + COUNT 231ms + 브랜드 0.2ms)
```

처음에는 Redis 연결 실패 비용을 의심했지만 아니었다. 집계 쿼리가 2.6초에서
5.9초로 느려진 것이 원인이고, 인덱스 105MB 가 버퍼 풀 128MB 를 나눠 쓰게 된
영향으로 보인다.

### 복구 후 재채움 — 처음에는 안 됐다

Redis 를 다시 올리고 `PING` 에 `PONG` 이 오고 복제도 정상(`master_link_status:up`)
인데도 **앱이 재연결하지 못했다.** 30초를 기다려도 요청마다 캐시 조회가 실패하고
키가 생기지 않았다. 앱을 재시작하니 즉시 복구됐다.

운영이라면 Redis 가 잠깐 끊긴 뒤 앱이 영원히 캐시 없이 도는 상태가 된다 —
가장 위험한 모양이다. **요청은 성공하므로 알림도 울리지 않는다.**

원인은 `LettuceConnectionFactory` 의 기본값이었다. 연결 하나를 공유하면서
(`shareNativeConnection = true`) 그 연결이 살아 있는지 확인하지 않는다
(`validateConnection = false`). 한번 끊기면 죽은 연결을 계속 내어준다.

`modules/redis/RedisConfig.kt` 에서 `validateConnection = true` 로 바꿨다.
연결을 내어주기 전에 `PING` 으로 확인하고 죽어 있으면 새로 만든다.

### 고치고 다시 재현

| | 결과 |
| --- | --- |
| ① 정상 | 2.52초(미스) → 0.23초(히트), 키 존재 |
| ② Redis 중지 | 1.78초 · `200` — DB 우회 |
| ③ Redis 복구 | **앱은 그대로 둔다** |
| ④ 재채움 | 0.24 / 0.27 / 0.24초, 키 존재 — **첫 요청부터 히트** |

`PING` 이 연산마다 한 번 더 들지만 ④의 0.24초가 고치기 전 히트(0.23초)와
거의 같아, 측정 가능한 수준의 차이는 보이지 않는다.

`modules/redis` 는 `commerce-api` · `batch` · `streamer` 가 함께 쓴다.
셋 다 같은 문제를 갖고 있었고 함께 고쳐진다.

이 과정에서 로그를 고쳤다. `cause.message` 만 남겨 `Redis exception` 한 줄로
끝나 무엇이 끊겼는지 알 수 없었다. 예외 타입과 가장 안쪽 원인까지 남긴다.

## 9. 아직 하지 않은 것

여기까지가 "집계 정렬을 없앴다" 의 범위다. 남은 항목을 적어둔다.

| | 무엇이 | 측정된 근거 |
| --- | --- | --- |
| 1 | **무효화 경로가 없다.** 3절에서 보듯 대상은 좋아요 하나지만, 그 하나를 아직 걸지 않았다. 순위 신선도는 TTL 60초로만 제한된다 | — |
| 2 | **TTL 만료에서 스탬피드가 난다.** 40 VU 에서 TTL 이 끝나는 순간 41개 요청이 동시에 미스를 맞고 같은 쿼리를 실행했다. 혼자면 2.6초인 쿼리가 **각각 20초**가 됐다 | p99 21.17s (40 VU · 90초) |
| 3 | **`totalCount` 가 이득을 깎는다.** 캐시가 못 건드리는 쿼리다. 매 요청이 100만 행을 센다. 부하 아래서 요청당 826ms | 826ms 평균 (40 VU) |
| 4 | ~~캐시 없는 상태의 부하 비교~~ — 6절에서 측정했다. 40 VU 에서 처리량 20배 · 응답시간 22배 | 완료 |
| 5 | ~~복구 후 재연결~~ — 7절에서 고쳤다. `validateConnection = true` 로 앱 재시작 없이 복구된다 | 완료 |

2번은 평균으로는 보이지 않는다 — 평균 1.16초, p95 1.20초인데 p99 만 21초다.

## 10. 테스트

`ProductSearchCacheIntegrationTest` 7개. Redis · MySQL testcontainer 를 쓴다.

히트를 확인하는 방법으로 모킹을 쓰지 않았다. **DB 를 바꿔도 순서가 그대로인지**로 본다.
캐시가 지난 순위를 들고 있다는 사실 자체가 검증 대상이기 때문이다.

| | |
| --- | --- |
| 미스에서 캐시가 채워진다 | |
| 히트에서 좋아요가 뒤집혀도 담아둔 순서로 반환한다 | hit 의 증거 |
| 버리면 바뀐 순서를 반영한다 | |
| 담아둔 상품이 판매중지되면 목록에서 빠진다 | 계약 유지 |
| 담아둔 상품이 삭제되면 목록에서 빠진다 | 계약 유지 |
| 조건이 다르면 서로 다른 캐시를 쓴다 | 키 분리 |
| 인기순이 아닌 정렬은 캐시를 거치지 않는다 | |
