결제 부하 기준선

서킷을 붙이기 전에, 서킷이 없을 때 무엇이 어떤 순서로 망가지는지 재둔다. PG 가 건강한 상태에서만 잰 값이다.

결제 수단 카드 · 정상 카드 ...1451 대상 commerce-api eaae4ea · :8099 PG pg-simulator 0.4.0 · 거절 1.1% DB MySQL 8 · product 100만 행 커넥션 풀 Hikari 40 · timeout 3s 톰캣 threads 200 · mbean 켬 PG 타임아웃 connect 1s · read 3s 부하 k6 1.2.3

처리량은 VU 1,000 에서 멈추고 10,000 에서 무너진다

전 단계를 30초로 맞췄다. 비교는 초당 확정 건수로 한다.

결제보다 남의 API 가 먼저 느려진다

결제만 보면 “PG 가 느리니 결제도 느리다”로 끝난다. 그래서 결제와 아무 상관 없는 요청을 두 종류 같이 쐈다. 둘로 나눈 이유는 느려진 원인이 갈리기 때문이다.

VU 100

결제는 아직 152ms 인데 상품 목록이 540 → 2,093ms. 남의 API 가 먼저 느려진다. 커넥션 풀은 이미 40/40 인데 톰캣 스레드는 113/200 으로 여유가 있다. 그래서 DB 를 쓰는 쪽만 느려지고 404 는 2ms 를 지킨다.

VU 1,000

톰캣 스레드 200개가 전부 풀 대기에 묶인다. 그 순간 DB 를 한 글자도 안 타는 404 가 2ms 에서 705ms로 간다. 결제가 다른 API 를 끌고 내려가는 경로가 이것이다.

VU 10,000

접수 단계에서 118,198건이 커넥션 리셋되고 확정은 1,833건만 끝났다. 그런데 상품 목록의 중앙값은 495ms 로 VU 1,000(2,724ms)보다 작다 — 들어온 것만 처리하기 때문이다. 같은 단계의 p99 는 14,519ms 다. 중앙값만 보는 감시 장치가 “건강하다”고 말하는 구간이 여기다.

커넥션 풀이 먼저 차고, 그 다음 스레드가 묶인다

PG 는 끝까지 멀쩡했다. 이번 실행에서 PG 관련 예외와 커넥션 획득 타임아웃은 모두 0건이다. 대기는 전부 3초 안에 풀렸고, 막힌 곳은 풀 40칸이었다.

10만 건 결제

동시 1,000 으로 총 100,000건. 10만 VU 는 이 머신에서 불가능하다 — k6 는 VU 당 약 290 KiB 를 쓰므로(1,000 VU 380 MiB·10,000 VU 2,829 MiB 실측) 10만 VU 는 약 29 GiB 다. 그래서 10만을 동시 수가 아니라 총량으로 돌렸다.

그래서 서킷이 필요한가 — 아직 모른다

두 번 다 PG 실패를 주입하지 않았다. 0건이 나온 게 아니라 만들지 않은 것이다. 지금 보이는 병목은 PG 가 아니라 우리 커넥션 풀이고, 서킷은 그걸 고쳐주지 않는다. 서킷의 근거는 장애 주입 측정에서 나온다 — 아래가 그 설계이며 아직 돌리지 않았다.

  1. docker pause pg-simulator · ...1111 카드 PG 가 느려짐 — read 타임아웃 3초 동안 톰캣 스레드가 묶이는가. light 가 같이 죽는가
  2. docker stop pg-simulator PG 가 죽음 — 연결 거부는 즉시 실패다. 느려짐보다 덜 아픈가
  3. docker unpause · docker start PG 가 되살아남 — 우리가 포기한 거래가 PG 에서는 확정돼 있는가
  4. ...0000 카드 정상 거절 — 실패지만 PG 는 건강하다. 서킷이 세면 안 되는 신호다
