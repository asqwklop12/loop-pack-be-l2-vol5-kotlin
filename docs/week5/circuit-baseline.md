# 결제 부하 기준선 — 서킷 없이, PG 가 건강할 때

서킷 임계값을 정하려면 "서킷이 없을 때 무엇이 어떻게 망가지는지"를 먼저 숫자로 알아야 한다.
이 문서는 그 측정이다. **PG 가 건강한 상태**에서만 재서, PG 가 아플 때와 비교할 바탕을 만든다.

**2회차(2026-10-18 19:37)가 기준이다.** 1회차와의 차이는 7절에 적었다.

두 번 다 PG 는 건강한 상태였다. 같은 시나리오를 반복한 것이지 장애를 주입한 것이 아니다.
PG 를 아프게 하는 측정은 아직 하지 않았고, 8절이 그 설계다.

## 1. 측정 환경

| 항목 | 값 |
| --- | --- |
| 머신 | Apple Silicon · 12 코어 · 32 GiB (다른 컨테이너가 이미 ~5 GiB 사용 중) |
| 대상 | `commerce-api` · 포트 8099 (개발용 8080 인스턴스와 분리) |
| PG | `pg-simulator` 0.4.0 · 컨테이너 · 거절 확률 1.1% |
| DB | MySQL 8.0 컨테이너 · `product` 100만 행 · `orders` 는 **비우고 시작** |
| 커넥션 풀 | HikariCP `maximum-pool-size: 40` · `connection-timeout: 3000ms` |
| 톰캣 | `threads.max: 200` · `accept-count: 100` · `mbeanregistry.enabled: true` |
| PG 타임아웃 | connect 1s · read 3s |
| 부하 | k6 v1.2.3 · `docs/week5/k6-payment-ramp.js` |

결제 수단은 카드(`method: CARD`)이고 카드번호는 정상 카드(`...1451`)다.
테스트 카드로 실패를 주입하지 않았고 `docker pause` · `stop` 도 누르지 않았다.

## 2. 재는 방법 — 레인 세 개

결제만 보면 "PG 가 느리니 결제도 느리다" 로 끝난다. 결제와 **상관없는** 요청을 같이 쏴야
전파가 보인다. 원인을 가르려고 둘로 나눴다.

| 레인 | 요청 | 한가할 때 | 느려지면 |
| --- | --- | --- | --- |
| payment | 주문 생성 → 확정(카드) → PG 접수 | — | 부하를 올리는 쪽 |
| heavy | `GET /api/v1/products?page=0&size=20` | 540ms | DB 쪽에서 밀린다 |
| light | `GET /api/v1/__ping` (404, DB 안 탐) | 1ms | 요청을 받아줄 여유가 없다 |

heavy · light 는 `constant-arrival-rate` 다. VU 를 공유하면 payment 가 VU 를 다 쥔 동안
요청을 못 보내서, 느려진 게 아니라 **안 보낸 것**이 된다.

## 3. 단계별 — 동시 VU 를 올린다

| VU | 시간 | 확정 완료 | **확정/s** | 409 | 5xx | 주문 생성 실패 | 결제 med | 결제 p99 | heavy med | heavy p99 | light med | light p99 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 100 | 30s | 9,304 | **310** | 11 | 3 | 1 | 152ms | 457ms | 2,093ms | 2,881ms | 2ms | 36ms |
| 1,000 | 30s | 18,461 | **615** | 16 | 0 | 904 | 825ms | 1,409ms | 2,724ms | 3,720ms | **705ms** | 856ms |
| 10,000 | 30s | 1,833 | **61** | 6 | 2 | **118,198** | 929ms | 1,468ms | 495ms | **14,519ms** | 489ms | 14,517ms |

**VU 100** — 결제는 152ms 인데 상품 목록이 540 → 2,093ms. **남의 API 가 먼저 느려진다.**

**VU 1,000** — `light` 가 2ms 에서 705ms 로 간다. DB 를 한 글자도 안 타는 404 가 느려졌다는
것은 요청을 받아 처리할 스레드가 없다는 뜻이다. 주문 생성 실패 904건은 커넥션 리셋이다.

**VU 10,000** — 붕괴. 접수 단계에서 118,198건이 리셋되고 확정은 1,833건만 끝났다.
처리량이 615 에서 **61 로 10분의 1**이 된다. 그런데 `heavy` 의 중앙값은 495ms 로 VU 1,000
(2,724ms)보다 **작다** — 들어온 것만 처리하기 때문이다. 중앙값만 보는 감시 장치가
"건강하다"고 말하는 구간이 여기다. 같은 단계의 p99 는 14,519ms 다.

### 어디가 먼저 차는가

| VU | tomcat busy | tomcat 스레드 | hikari active | hikari 대기 |
| --- | --- | --- | --- | --- |
| 100 | 113 / 200 | 116 | **40 / 40** | 73 |
| 1,000 | **200 / 200** | 200 | 40 / 40 | 160 |
| 10,000 | **200 / 200** | 200 | 40 / 40 | 160 |

순서가 분명하다. **커넥션 풀이 먼저 찬다.** VU 100 에서 풀은 이미 40/40 이고 73개가 대기
중인데, 톰캣 스레드는 아직 113/200 으로 여유가 있다. 그래서 이 단계에서는 DB 를 쓰는
`heavy` 만 느려지고 `light` 는 2ms 를 지킨다.

VU 1,000 에서 **스레드 200개가 전부 풀 대기에 묶인다.** 그 순간 DB 와 무관한 `light` 까지
705ms 가 된다. 결제가 다른 API 를 끌고 내려가는 경로가 이것이다.

커넥션 획득 타임아웃(`connection-timeout: 3000ms` 초과)은 VU 10,000 에서 2건 났다.
그 밖에 MySQL 이 커넥션을 닫아 `No operations allowed after connection closed` 도 나왔다.

## 4. 10만 건 결제

동시 1,000 으로 총 100,000건. 10만 **VU** 는 이 머신에서 불가능하다 — k6 는 VU 당 약 290 KiB 를
쓰므로(1,000 VU 380 MiB · 10,000 VU 2,829 MiB 실측) 10만 VU 는 약 29 GiB 다.
그래서 10만을 동시 수가 아니라 총량으로 돌렸다.

| 항목 | 값 |
| --- | --- |
| 시도 | 100,000 |
| 확정 완료 | 98,381 |
| 409 (낙관적 잠금 충돌) | 62 |
| 5xx | 0 |
| 주문 생성 실패 | 1,557 (1.6%) |
| 실제 소요 | **191초** (커넥션 풀이 바빴던 구간으로 역산) |
| 확정 처리량 | **515 확정/s** |
| 결제 확정 | med 916ms · p99 1,879ms |

heavy · light 의 median 은 이 실행에서 **의미가 약하다.** control 레인을 4분으로 잡아
결제가 끝난 뒤에도 돌았고, 한가한 구간이 섞인다. p99 만 부하 구간을 반영한다.

## 5. 곁에서 나온 것 — 낙관적 잠금

`ObjectOptimisticLockingFailureException` 이 95건 발생했다. 같은 상품에 동시 확정이 몰려
`@Version` 이 하나를 거절한 것이다. `ApiControllerAdvice` 가 `CONFLICT` 로 매핑하므로
응답은 **409** 이며 500 이 아니다.

상품 20,000개에 요청을 퍼뜨렸는데도 생겼다. 상품을 좁히면 이 숫자가 지배할 것이다.

## 6. 측정 중에 고친 것

| # | 문제 | 고친 내용 |
| --- | --- | --- |
| 1 | control 레인을 상품 목록 하나로만 뒀다. 한가할 때도 540ms 라 느려진 원인이 DB 인지 스레드인지 갈리지 않았다 | DB 를 타지 않는 `light` 레인(404)을 추가했다 |
| 2 | `tomcat_threads_*` 가 없는데 0 으로 읽고 "스레드는 한가했다" 고 결론 낼 뻔했다 | `server.tomcat.mbeanregistry.enabled=true` 로 켰다. 2회차에서 실제 값을 얻었다 |
| 3 | 총량 모드에서 control 레인이 payment 보다 오래 돌아 median 이 희석됐다 | `RUN_FOR` 로 두 레인의 길이를 묶었다 |
| 4 | 확정 URL 이 주문마다 달라 k6 메트릭 카디널리티 경고가 났다 | `name` 태그로 묶었다 |
| 5 | 단계마다 시간이 달랐는데(1회차의 VU 10,000 만 20초) 건수를 한 표에 나란히 뒀다 | 2회차는 전 단계를 30초로 맞췄고, 비교는 **확정/s** 로 한다 |
| 6 | 전략 패턴 도입 후 k6 가 `method` 를 안 보내 **포인트 결제로 가고 있었다.** 포인트가 없는 유저라 측정 자체가 무의미해질 뻔했다 | 요청 본문에 `method: 'CARD'` 를 넣었다 |
| 7 | 집계 스크립트가 `tomcat_threads_busy` 로 찾았는데 실제 이름은 `tomcat_threads_busy_threads` 였다. 또 0 으로 읽었다 | 키 이름을 맞췄다. **없는 키를 0 으로 읽는 실수를 세 번 반복했다** |

## 7. 같은 시나리오를 두 번 돌린 결과 — 이 숫자는 재현되지 않는다

| | 1회차 (PG 0.2.0) | 2회차 (PG 0.4.0) |
| --- | --- | --- |
| VU 100 확정/s | 615 | **310** |
| VU 1,000 확정/s | 638 | 615 |
| VU 10,000 확정/s | 53 (20초) | 61 (30초) |
| 10만 건 | 152초 · 638/s | **191초 · 515/s** |
| 커넥션 획득 타임아웃 | 0 | 2 |

VU 100 이 절반이 됐고 10만 건도 느려졌다. 조건이 셋 달라졌다 — PG 가 0.4.0(거절 확률
1.1% · 금액 비교)이 됐고, `orders` 를 비우고 시작했고(1차는 측정 중 계속 커졌다),
머신 상태도 다르다. **어느 쪽이 원인인지 이 데이터로는 가를 수 없다.**

흔들리는 원인은 더 있다. k6 가 상품을 `Math.random()` 으로 고르므로 낙관적 잠금 충돌
횟수가 매번 다르고, 같은 머신에서 mysql · kafka · grafana 가 함께 돈다.

처리량은 비슷하게 재현되지만 **p99 는 크게 흔들린다.** 꼬리는 원래 표본마다 변한다.
`heavy p99 14,519ms` 같은 값을 하나의 숫자로 믿으면 안 된다.

## 8. 아직 재지 않은 것 — 장애 주입 측정

두 번 다 **PG 실패를 주입하지 않았다.** 0건이 나온 게 아니라 만들지 않은 것이다.
따라서 이 문서는 서킷이 필요한 이유를 **아직 보여주지 않는다.** 지금 보이는 병목은
PG 가 아니라 우리 커넥션 풀이고, 서킷은 그것을 고쳐주지 않는다.

**장애 주입 측정**에서 같은 부하에 아래를 섞는다. 이름을 따로 붙인 이유는, 위의 1·2회차와
섞어 부르면 "2차로 재야 나온다" 가 "그냥 한 번 더 돌린다" 로 읽히기 때문이다.

| 섞을 것 | 수단 | 보려는 것 |
| --- | --- | --- |
| PG 가 느려짐 | `docker pause pg-simulator` 또는 `...1111` 카드 | read 타임아웃 3초 동안 톰캣 스레드가 묶이는가. `light` 가 같이 죽는가 |
| PG 가 죽음 | `docker stop pg-simulator` | 연결 거부는 즉시 실패다. 느려짐보다 **덜** 아픈가 |
| PG 가 되살아남 | `docker unpause` / `start` | 포기한 거래가 PG 에서 확정돼 있는가 |
| 정상 거절 | `...0000` 카드 | 실패지만 PG 는 건강하다. 서킷이 세면 안 되는 신호다 |

그 숫자가 나오면 실패율 몇 %, 몇 회, 열린 뒤 몇 초 대기인지를 근거와 함께 정할 수 있다.

## 9. 적재된 데이터

측정마다 `orders` · `order_line` 에 수십만 행이 쌓인다. 지우려면 아래를 돌린다.

```sql
SET FOREIGN_KEY_CHECKS = 0;
TRUNCATE TABLE order_line;
TRUNCATE TABLE orders;
SET FOREIGN_KEY_CHECKS = 1;
```
