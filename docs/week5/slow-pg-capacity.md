# 느린 PG 와 우리 용량 — 리틀의 법칙으로 역산하기

장애 주입 측정(`fault-injection.html`)은 PG 를 **멈추거나 죽여서** 쟀다.
이 문서는 그 사이, **느리지만 살아 있는 PG** 를 잰다. 실제로 가장 흔한 고장이다.

질문은 하나다 — **PG 가 느려지면 우리는 몇 명까지 버티나.**

## 1. 측정 환경

| 항목 | 값 |
| --- | --- |
| 날짜 | 2026-10-20 |
| PG | `pg-simulator` 0.5.0 · `PG_RESPONSE_DELAY=10s` (모든 접수가 10초 지연) |
| 대상 | `commerce-api` · 포트 8099 |
| PG 타임아웃 | connect 1s · **read 3s** |
| 커넥션 풀 | HikariCP 40 · `connection-timeout: 3000ms` |
| 톰캣 | threads 200 |
| 결제 수단 | 카드 · 정상 카드(`...1451`) |
| 부하 | k6 · 각 단계 30초 |

`PG_RESPONSE_DELAY` 는 0.5.0 에서 추가했다. 그전에는 `...1111` 테스트 카드만 느려서
**모든 결제를 느리게 할 수단이 없었다.**

> **버린 측정이 있다.** 첫 VU 20 실행은 MySQL 이 23시간 전에 내려가 있어 전부 실패로
> 나왔다. PG 와 무관한 값이라 버리고, DB 를 올린 뒤 다시 쟀다. 아래는 재측정값이다.

## 2. 측정값

| VU | 결제 확정 | 5xx | 결제 med | 상품목록 med | 404 med | 톰캣 busy | 풀 대기 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 한가할 때 | — | — | — | **540ms** | 1ms | — | — |
| 20 | 0 | 200 | 3,037ms | 756ms | 3ms | 28 / 200 | 0 |
| 50 | 0 | 396 | 3,308ms | **4,087ms** | 3ms | 76 / 200 | **36** |

결제는 두 단계 모두 **0건 성공**이다. PG 응답이 10초인데 read 타임아웃이 3초라 전부 끊긴다.

**VU 20** — 결제는 전멸인데 상품 목록은 756ms 로 거의 멀쩡하다. 풀 대기 0.

**VU 50** — 상품 목록이 540 → **4,087ms**. 풀 대기 36 이 생긴다.
톰캣 스레드는 76/200 으로 여유가 있는데도 그렇다 — **커넥션이 먼저 말랐다.**

**404 는 끝까지 3ms 다.** DB 를 타지 않으니 멀쩡하다. 병목이 스레드가 아니라
커넥션이라는 증거다.

### 다른 PG 상태와 나란히

| PG 응답 | 무너지는 VU | 그때 상품목록 |
| --- | --- | --- |
| 0.1초 (정상) | 1,000 | 3,046ms |
| **10초** | **50** | 4,087ms |
| 멈춤 (`docker pause`) | 1,000 | 15,576ms |
| 죽음 (`docker stop`) | — | 529ms |

**느릴수록 적은 부하로 터진다.** PG 가 정상일 때 VU 1,000 이 필요했던 피해가
10초로 느려지면 VU 50 에서 난다. 20배 적은 트래픽이다.

같은 코드인데 **남의 응답 시간 하나로 버티는 범위가 20배** 달라진다.
우리 트래픽을 아무리 잘 예측해도 막을 수 없는 종류의 사고다.

## 3. 리틀의 법칙으로 검산

`L = λ × W` — 시스템에 동시에 머무는 수는 처리율 곱하기 체류 시간이다.

| VU | 처리율 λ | 체류 W | L = λ×W | 실제 VU |
| --- | --- | --- | --- | --- |
| 20 | 6.7/s | 3.04초 | **20.2** | 20 |
| 50 | 13.2/s | 3.31초 | **43.7** | 50 |

VU 20 은 거의 정확히 20 이 나온다. **모든 VU 가 항상 결제에 묶여 있다**는 뜻이다.
VU 50 이 43.7 로 모자란 것은 여섯 개쯤이 주문 생성 중이라 결제 구간 밖에 있었기 때문이다.

### 상한은 커넥션이 정한다

VU 50 의 처리율 13.2/s 는 우연이 아니다.

```
커넥션 40 ÷ 체류 3.04초 = 13.2 건/s
```

VU 를 더 올려도 이 숫자는 오르지 않고 **대기만 늘어난다.** 측정에서 풀 대기 36 이
생긴 것이 그 신호다. VU 50 에서 이미 포화였다.

## 4. 역산 — 타임아웃을 얼마로 잡을 것인가

지금까지 쓴 read 타임아웃 3초에는 **아무 근거가 없었다.** 리틀의 법칙을 뒤집으면 근거가 나온다.

### 타임아웃을 줄이면 처리량이 얼마나 오르나

| 체류 시간 | 결제 최대 처리율 |
| --- | --- |
| 3.04초 (지금) | 13.2/s |
| 2초 | 20/s |
| 1초 | 40/s |
| 0.5초 | 80/s |
| 0.1초 (PG 정상) | 400/s |

**타임아웃이 곧 처리량이다.** 3초를 0.5초로 줄이면 6배가 된다.

### 트래픽이 주어졌을 때 타임아웃의 상한

결제에 커넥션 20칸만 내주고 나머지 20칸을 조회 몫으로 남긴다면:

| 결제 트래픽 | 타임아웃을 이보다 짧게 |
| --- | --- |
| 5건/s | 4초 |
| 10건/s | 2초 |
| 20건/s | 1초 |
| 40건/s | 0.5초 |

```
타임아웃 = 결제에 허용한 커넥션 ÷ 결제 트래픽
```

이것이 "몇 초로 잡을까" 의 근거다.

## 5. 이 계산이 전제하는 것

위 식은 **결제가 커넥션을 쥔 채 PG 를 기다린다**는 전제 위에 있다.
지금 `OrderFacade.confirm` 이 `@Transactional` 안에서 PG 를 부르기 때문이다.

PG 호출을 트랜잭션 밖으로 빼면 체류 `W` 에서 PG 대기가 빠지고 DB 작업 시간만 남는다.
그러면 이 계산 자체가 느슨해지고, 커넥션은 더 이상 상한이 아니게 된다.

**그래서 트랜잭션 분리가 타임아웃 조정보다 먼저다.** 타임아웃을 먼저 줄이면
같은 구조에서 숫자만 당기는 것이고, 분리를 하면 식의 전제가 바뀐다.

## 6. 아직 하지 않은 것

| | 무엇을 |
| --- | --- |
| 1 | 트랜잭션 분리 후 재측정 — 같은 VU 50 에서 상품목록이 얼마나 회복되는지 |
| 2 | 타임아웃을 0.5초로 줄인 뒤 재측정 |
| 3 | 서킷 — 위 둘로도 남는 피해를 끊는다 |
| 4 | 결제만 쓰는 커넥션·스레드를 따로 제한(bulkhead) — 조회 몫을 보장하는 다른 길 |

4번은 서킷과 성격이 다르다. 서킷은 "PG 가 아플 때" 막고, bulkhead 는 "결제가 많을 때" 도 막는다.
PG 가 멀쩡한데도 VU 1,000 에서 조회가 밀렸던 것은 후자다.
