# 결제 한 흐름 부하 — 주문부터 콜백까지

앞선 측정들은 **PG 가 고장났을 때** 우리가 어떻게 무너지는지 쟀다.
이 문서는 반대쪽을 잰다 — **PG 가 정상일 때 한 흐름이 끝까지 도는가,**
그리고 **돈이 맞는가.**

한 흐름은 이렇게 돈다.

```
주문 생성 → 주문 확정(카드) → PG 접수(202 PENDING) → PG 확정 → 콜백 → SUCCESS / FAILED
```

앞의 네 단계는 동기다. 마지막 두 단계는 PG 가 **나중에** 콜백으로 알려준다.
그래서 부하가 끝난 직후에 결제 테이블을 세면 **전부 PENDING** 이다.
콜백이 수렴할 때까지 기다린 뒤에 세야 성공·실패 숫자가 나온다.

## 1. 측정 환경

| 항목 | 값 |
| --- | --- |
| 날짜 | 2026-10-21 |
| PG | `pg-simulator` 0.5.0 · `PG_RESPONSE_DELAY=0s` · `PG_CALLBACK_DELAY=3s` |
| 거절 확률 | 한도 0.5% · 잔액 0.5% · 분실 0.1% (합 1.1%) |
| 대상 | `commerce-api` · 포트 8099 (관리 8098) |
| PG 타임아웃 | connect 1s · read 3s |
| 커넥션 풀 | HikariCP 40 · `connection-timeout: 3000ms` |
| 톰캣 | threads 200 |
| 결제 수단 | 카드 · 정상 카드(`...1451`) |
| 부하 | k6 · 30초 · 세 레인(결제 / 상품목록 / 404) |
| 초기화 | 단계마다 `orders` · `order_line` · `payment` truncate |

## 2. 단계별 결과

단계마다 `orders` · `order_line` · `payment` 를 비우고, **PG 컨테이너도 같이 재기동**한다
(이유는 5절).

사다리는 **VU 100 에서 멈춘다.** 이유는 13절에 적었다 — 그 위로는 숫자가 대상이 아니라
부하 장치를 재기 시작한다.

## 3. 읽은 것

### 결제는 가볍고, 남의 API 가 먼저 느려진다

VU 10 에서 확정은 med 19ms 인데 상품 목록은 한가할 때 540ms 짜리가 **1,063ms** 가 됐다.
결제 레인이 쓴 것은 자기 응답 시간이 아니라 **남이 쓸 DB 시간**이다.

### 커넥션 풀이 스레드보다 먼저 마른다

세 레인을 따로 쏜 이유가 여기서 값을 한다.

| VU | 404 | 읽은 것 |
| ---: | ---: | --- |
| 10 | 1.3ms | DB 만 밀린다. 스레드는 한가하다 (19/200) |
| 100 | 1.1ms | **커넥션 풀이 마른다** (40/40 · 대기 70). 스레드는 110/200 로 아직 여유 |

VU 100 에서 풀은 꽉 찼는데 스레드는 절반이다. 앞선 느린-PG 측정과 같은 결론이다 —
**지켜야 하는 자원의 순서는 커넥션이 먼저다.**

404 가 1.1ms 로 멀쩡한 것도 같은 말이다. DB 를 타는 경로만 밀렸다는 뜻이고,
스레드가 마르기 시작하면 404 부터 같이 느려질 것이다.

커넥션 획득 실패는 두 단계 모두 **0** 이다. 대기는 생기지만 3초 안에 다 받아낸다.
정상 PG 에서는 점유시간이 짧아 풀이 돌아가기 때문이다.

### 콜백이 같이 밀린다

콜백 처리율이 **525 → 396 /s** 로 떨어진다.
PG 의 콜백 발신은 **단일 스레드 직렬**이고, 한 건마다 우리 API 로 POST 를 쏜다.
우리 API 가 포화되면 그 POST 가 느려지고, **뒤에 줄 선 콜백 전부가 같이 밀린다.**

VU 100 에서는 부하가 끝난 뒤 **약 46초** 동안 결제가 미확정으로 남아 있었다.
주문은 이미 CONFIRMED 인데 결제는 PENDING 인 창이 그만큼 열려 있었다는 뜻이다.
돈은 결국 맞았지만, **맞기까지 걸린 시간**이 부하에 비례해 늘어난다.

여기서 나오는 말은 하나다 — 콜백은 **늦게 올 수 있다**는 전제를 깔아야 한다.
"확정은 콜백이 온다" 가 아니라 "콜백이 안 오면 조회로 대조한다" 가 필요한 이유다.

## 4. 어디까지 쓸 수 있나

| VU | 상태 |
| ---: | --- |
| 10 | 멀쩡하다. 자원 10% 아래 |
| 100 | **커넥션 풀이 한계**. 상품 목록 1.4초. 콜백 46초 지연. 돈은 다 맞는다 |

**VU 100 이 이미 한계선이다.** 풀이 꽉 차고 대기 70 이 생긴다.
돈이 다 맞는 것과 자원이 남는 것은 다른 얘기다 — 지금은 맞지만 여유가 없다.

## 5. 걸린 것 — truncate 와 PG 의 기억

`orders` 를 truncate 하면 auto_increment 가 1부터 다시 시작한다.
그런데 **PG 는 orderId 를 메모리에 들고 있다.** 앞 단계에서 접수한 주문 번호가
남아 있으면, 같은 번호에 다른 금액이 들어오자 "같은 주문에 다른 금액" 으로 **409** 가 난다.

PG 의 멱등 장치가 제대로 동작한 것이고 고칠 쪽은 측정 절차다 —
**단계마다 PG 컨테이너도 같이 재기동해 저장소를 비운다.**

이게 실제 설계에 주는 말도 있다. 우리 쪽에서 orderId 를 재사용하면
PG 는 그것을 **같은 거래의 재시도로 읽는다.** 주문 번호는 지우고 다시 쓸 수 있는
번호가 아니다.

> **측정 주의.** 수렴 대기는 PENDING 이 같은 값으로 몇 번 읽혔다고 끝난 것이 아니다.
> 콜백 발신이 단일 스레드라 느린 POST 에 걸리면 **뭉쳐서 빠진다.** 멈춘 것처럼 보인다.

# 고장 — PG 가 10초 걸릴 때

여기부터는 같은 사다리를 **`PG_RESPONSE_DELAY=10s`** 로 다시 올린다.
PG 는 죽지 않았다. **살아 있는데 느리다.**

우리 read 타임아웃은 3초다. PG 는 10초에 답한다. 그래서 **모든 카드 결제가 끊긴다.**
끊기면 확정 트랜잭션이 롤백되고 `payment` 행도 사라진다 — **그런데 PG 는 그 결제를 들고 있다.**

그래서 이 측정은 우리 쪽만 세면 안 된다. **PG 쪽에 남은 거래까지 세야** 구멍이 보인다.
`GET /api/v1/payments?orderId=` 로 주문 번호를 1부터 끝까지 훑어서 셌다.

## 6. 돈이 어디로 갔나

| VU | 주문 | 확정 | 우리 `payment` 행 | 우리가 받은 돈 | PG 거래 | PG SUCCESS | **PG 가 승인한 금액** |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 10 | 100 | **0** | **0** | **0원** | 100 | 98 | **5,764,609원** |
| 100 | 627 | **0** | **0** | **0원** | 439 | 432 | **27,572,299원** |

주문은 전부 DRAFT 로 남고, 우리 결제 기록은 **두 단계 모두 0행**이다.
정상 PG 에서 미확정이 0 이었던 것과 숫자는 같은데, 뜻이 정반대다 —
그때는 **다 확정됐다**는 0 이고, 지금은 **아무것도 기록되지 않았다**는 0 이다.

그리고 PG 쪽에는 **승인된 결제가 쌓여 있다.** VU 10 에서도 98건 · 576만원,
VU 100 에서 432건 · 2,757만원이다. 가장 작은 부하에서도 그렇다.

**이게 이번 주차가 막으려는 사고다.** 롤백은 우리 DB 만 되돌린다.
남의 시스템에 이미 넘어간 승인은 되돌려주지 않는다.

PG 거래가 주문 수보다 적은 것(627 → 439)도 읽을 값이다.
188건은 **PG 를 부르기도 전에** 커넥션을 못 받아 죽었다.

## 7. 속도

| VU | 주문 생성 med | 주문 확정 med | 상품 목록 med | 404 med |
| ---: | ---: | ---: | ---: | ---: |
| 10 | 10ms | **3,013ms** | 520ms | 2.0ms |
| 100 | 852ms | 3,594ms | **6,358ms** | 2.1ms |

확정 med 가 VU 10 에서 이미 **3,013ms** 다. 타임아웃 3초에 정확히 붙었다.
**모든 결제가 3초를 꽉 쓰고 실패한다** — 확정 5xx 가 100건 / 627건으로 전건이다.

VU 100 에서는 확정이 3,594ms 로 타임아웃보다 길다. PG 를 더 기다린 것이 아니라
**그 앞에서 커넥션을 기다린** 시간이 붙은 것이다.
주문 생성도 852ms 로 느려졌다 — 결제와 같은 풀을 쓰기 때문이다.

404 는 두 단계 모두 2ms 다. DB 를 타지 않는 경로는 멀쩡하다.
**스레드가 아니라 커넥션이 말랐다**는 뜻이다.

## 8. 자원 — 정상일 때와 비교

| VU | 톰캣 busy | 히카리 active | 풀 대기 | 커넥션 획득 실패 |
| ---: | ---: | ---: | ---: | ---: |
| 10 | 14 / 200 | 14 / 40 | 0 | 0 |
| 100 | 138 / 200 | **40 / 40** | 98 | **276** |

| 지표 (VU 100) | 정상 PG | 10초 PG |
| --- | --- | --- |
| 커넥션 획득 실패 | **0** | **276** |
| 상품 목록 med | 1,363ms | **6,358ms** |
| 톰캣 busy | 110 / 200 | 138 / 200 |
| 받아낸 돈 | 1,138,453,572원 | **0원** |

**정상 PG 에서는 대기만 생기고 다 받아냈는데, 10초 PG 에서는 VU 100 부터 못 받는다.**
결제 하나가 커넥션을 3초씩 쥐고 있으니, 40개 풀로는 초당 13건밖에 못 돌린다.

### 결제가 조회를 끌고 내려간다

같은 시점에 인기순 목록도 1초마다 찍었다.

| VU | 200 | 비200 | med | max |
| ---: | ---: | ---: | ---: | ---: |
| 10 | 26 | 0 | 190ms | 297ms |
| 100 | 5 | **4** | 204ms | 8,861ms |

VU 100 에서 9번 중 **4번이 500** 이다. 터진 시각이 3.00초 · 3.01초 · 5.14초 · 5.96초 —
3초는 히카리 `connection-timeout` 이다. **커넥션을 못 받아서 500 이다.**

정상 PG 에서는 같은 VU 100 에서 비200 이 0건이었다.
조회 쪽 코드는 그대로다. 달라진 것은 **풀에 자리가 있는지**뿐이다.

결제가 느려지면 결제만 실패하는 것이 아니다. 같은 풀을 쓰는 **읽기 API 가 같이 500 을 뱉는다.**
그래서 이번 주차에 지켜야 하는 자원은 스레드가 아니라 커넥션이다.

## 9. 읽은 것

### 느린 PG 는 죽은 PG 보다 나쁘다 — 다시 확인

PG 가 죽으면 연결이 즉시 거부돼 커넥션을 쥐는 시간이 짧다.
느리면 **3초씩 쥐고 있다.** 필요한 자리가 그만큼 늘어난다.

```
필요한 커넥션 = 결제 처리율 × 커넥션 점유시간
```

VU 100 에서 우리는 초당 **17.1건**을 확정 시도했고, 한 건이 3초를 쥐었다.
17 × 3 = **51개** 가 필요한데 풀은 **40개**다. 그래서 276건이 커넥션을 못 받았다.

VU 10 은 초당 3.3건이다. 3.3 × 3 = 10개 — 40개 안에 들어오므로 획득 실패가 0 이다.
같은 식이 두 단계를 다 설명한다.

### 롤백은 우리 쪽 거짓말이다

우리 장부는 깨끗하다 — 주문 DRAFT, 결제 0행, 받은 돈 0원. 모순이 없다.
**PG 장부에는 VU 100 한 번에 2,757만원이 승인돼 있다.**

양쪽 장부가 각자 일관된데 서로 다르다. 이걸 찾아내는 방법은 하나뿐이다 —
**대조(reconciliation).** PG 에 조회를 걸어 우리가 모르는 거래를 찾아오는 것.
이번 측정에서 내가 `orderId` 로 PG 를 훑은 그 행위가 바로 대조다.
지금은 측정 스크립트가 손으로 했고, 코드에는 없다.

### 콜백은 허공으로 떨어졌다

PG 는 3초 뒤 결제를 확정하고 우리에게 콜백을 보냈다.
우리 `PaymentCallbackHandler` 는 그 주문의 PENDING 결제를 찾는데,
**롤백돼서 행이 없다.** 그래서 아무것도 하지 않고 끝난다.

터지지는 않는다(그 경로는 테스트로 막아 뒀다). 하지만 **콜백이 가져온 정보가 버려진다.**
PG 는 "이 주문 승인했다" 고 알려줬는데 우리는 들을 그릇이 없었다.

여기서 순서가 나온다. **결제 기록을 먼저 남기고 PG 를 불러야 한다.**
지금은 한 트랜잭션 안에서 둘을 같이 하니, PG 호출이 실패하면 기록도 같이 사라진다.

## 10. 그래서 고칠 순서

측정이 가리키는 순서는 이렇다.

| 순서 | 할 일 | 이 측정이 주는 근거 |
| ---: | --- | --- |
| 1 | **트랜잭션 분리** — 결제 기록을 먼저 커밋하고 PG 호출 | 롤백으로 기록이 사라져 `payment` 0행 · 콜백이 허공으로 |
| 2 | **타임아웃 축소** | 3초가 커넥션 점유시간이다. 17 × 3 = 51 > 40 |
| 3 | **서킷** | 두 단계 모두 확정 100% 실패. 끊어도 잃을 게 없다 |
| 4 | **조회 대조** | PG 에 2,757만원이 떠 있고 우리는 모른다 |

1번이 먼저인 이유가 있다. 2번의 계산식(`처리율 × 점유시간`)은
**커넥션을 PG 대기 중에 쥐고 있다**는 전제 위에 서 있다.
트랜잭션을 분리하면 그 전제가 사라지므로, 타임아웃 값을 먼저 정해봐야 다시 정해야 한다.

> **측정 주의.** 부하를 끊어도 서버는 계속 처리한다. 톰캣 수용 큐에 쌓여 있던 요청이
> 뒤늦게 실행되면서 주문과 PG 거래가 계속 늘어난다.
> **k6 가 끝난 시점에 센 숫자는 최종값이 아니다.** 위 표는 수렴한 뒤에 다시 센 값이다.

# 결제 없이 목록만

앞의 측정은 결제와 목록을 같이 쐈다. 목록이 느려진 것이 **결제 탓인지 원래 그런지**
가르려면 목록만 쏴 봐야 한다. 같은 사다리를 결제 없이 올린다.

레인은 하나다 — `GET /api/v1/products?page=0&size=20`. VU 가 끝나는 대로 계속 밀어넣는다
(`constant-vus`). 앞 측정의 heavy 레인은 초당 5건으로 묶여 있었으므로 숫자를 바로
비교하면 안 된다.

## 11. 기본 정렬 (`created_at desc`)

| VU | med | p95 | max | 처리율 | 성공 | 실패 |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 10 | 729ms | 1,109ms | 1,412ms | 12.9 /s | 394 | 0 |
| 100 | 6,727ms | 8,645ms | 10,786ms | 14.7 /s | 469 | 31 |

**처리율이 VU 와 무관하게 고정이다.** VU 를 10배 올려도 12.9 → 14.7 /s 다.
느려진 것이 아니라 **줄을 선 것**이다. 리틀의 법칙을 응답 시간 쪽으로 돌리면 맞는다.

| VU | 실측 med | `L ÷ λ` |
| ---: | ---: | ---: |
| 10 | 711ms | 730ms |
| 20 | 1,410ms | 1,471ms |
| 40 | 2,812ms | 2,904ms |
| 60 | 3,909ms | 4,025ms |
| 100 | 5,913ms | 6,129ms |

오차 3% 안이다. 처리 능력이 14 /s 로 고정이니 동시에 100명이 들어오면
100 ÷ 14 = 7초를 기다린다.

### 그 14 /s 가 어디서 막히나

자원이 아니다. VU 10 에서 이미 14 /s 인데 그때 커넥션은 10개 · 스레드는 10개다.
풀 40 도 스레드 200 도 건드리지 않았는데 천장이다. 쿼리였다.

| 쿼리 | 계획 | 단독 비용 |
| --- | --- | ---: |
| 페이지 | `ALL` + `Using filesort` — 100만 행 읽고 전부 정렬 | 약 260ms |
| 전체 건수 | `ALL` — 100만 행 스캔 | 약 190ms |

목록 한 번에 100만 행을 두 번 읽고, 그중 한 번은 정렬까지 한다.
`idx_product_brand_price` 가 안 먹는 이유는 선두가 `brand_id` 인데
**브랜드 조건 없이 전체를 보는 요청**이라 인덱스에 들어갈 입구가 없기 때문이다.

### 인덱스를 걸어 보면

`(status, deleted_at, created_at desc, id desc)` 를 걸고 다시 쟀다.

| VU | med | 처리율 | 커넥션 획득 실패 |
| ---: | ---: | ---: | ---: |
| 10 | 729 → **182ms** | 12.9 → **53.7 /s** | 0 → 0 |
| 100 | 6,727 → **1,698ms** | 14.7 → **57.5 /s** | 31 → **0** |

두 쿼리가 모두 `ref` + `Using index` 로 바뀐다. 테이블을 아예 읽지 않는다.
`filesort` 가 사라진 쪽에서 거의 다 벌었다 — 페이지 쿼리가 260ms → 10ms 다.

4주차에 `(status, deleted_at)` 를 **선택도 82% 라 지운 판단과 충돌하지 않는다.**
그때는 거르는 용도로 봤고, 이건 **정렬을 건너뛰는 용도**다. 거르는 힘이 약해도 값을 한다.

> 이 인덱스는 측정 뒤 **다시 제거했다.** 엔티티 선언도 넣지 않았다.
> 쓸지 말지는 4주차 결론 위에서 따로 정해야 한다.

## 12. 인기순 (`likes_desc`)

| VU | med | p95 | p99 | max | 처리율 | 성공 | 실패 |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 10 | 220ms | 270ms | 315ms | 364ms | 44.3 /s | 1,337 | 0 |
| 100 | 2,173ms | 2,730ms | 3,093ms | 3,761ms | 45.3 /s | 1,445 | 0 |

| VU | 톰캣 busy | 히카리 active | 풀 대기 | 커넥션 획득 실패 |
| ---: | ---: | ---: | ---: | ---: |
| 10 | 10 / 200 | 10 / 40 | 0 | 0 |
| 100 | 100 / 200 | **40 / 40** | 60 | 0 |

**인기순이 기본 정렬보다 3.4배 빠르다.**

| VU | 기본 정렬 | 인기순 |
| ---: | ---: | ---: |
| 10 | 12.9 /s | **44.3 /s** |
| 100 | 14.7 /s | **45.3 /s** |

뒤집힌 것처럼 보이지만 이유가 있다. 상위 20개는 **캐시가 답하고**, 캐시를 채울 때도
`product_stats` 의 `(like_count desc, product_id desc)` 인덱스에서 id 만 뽑는다.
기본 정렬은 캐시가 없어 매번 100만 행을 읽고 정렬한다.

### 그래도 44 /s 가 천장이다

캐시 히트가 대부분인데도 막힌다. 남은 것이 **전체 건수 쿼리**다 —
`countBy` 는 정렬과 무관하게 매 요청마다 100만 행을 훑는다.

```
인기순 단건 220ms  =  건수 쿼리 약 190ms  +  나머지 약 30ms
```

캐시로 줄인 것은 30ms 쪽이고, **남은 86% 는 건수 세기**다.
인기순을 아무리 빠르게 만들어도 이 바닥은 넘지 못한다.

## 13. 사다리를 VU 100 에서 멈춘 이유

VU 1,000 부터는 측정이 대상을 재지 않는다.

`constant-vus` 는 1,000개 VU 를 **동시에 깨우고**, 각 VU 가 그 순간 소켓을 연다.
1초에 1,000개 연결 요청이 들어오는데 이 머신의 리슨 큐는
`kern.ipc.somaxconn` 128 이다. 넘친 연결은 커널이 핸드셰이크까지 받아 두고
큐에 못 넣어서, 요청 데이터가 도착할 때 RST 로 끊는다.
클라이언트가 보는 것이 `read: connection reset by peer` 다.

같은 1,000 VU 를 **20초에 걸쳐 올리면 실패가 0** 이다. 처리율은 같다.

| 투입 방식 | 404 성공 | 404 실패 | 처리율 |
| --- | ---: | ---: | ---: |
| 즉시 1,000 | 76,931 | **2,325** | 3,916 /s |
| 20초에 걸쳐 1,000 | 150,209 | **0** | 3,734 /s |

실패 시각도 전부 **테스트 시작 1초**에 몰려 있다. 그 뒤로는 keep-alive 로
연결을 재사용하니 끝까지 멀쩡하다. 부하가 아니라 **연결을 한꺼번에 연 탓**이다.

그래서 VU 1,000 구간의 실패율은 성질이 아니라 분모의 문제이기도 했다 —
첫 1초의 실패 건수는 비슷한데, 그 뒤에 쌓이는 성공 건수가 경로마다 수십 배 다르다.

**VU 10 · 100 만 남긴 이유가 이것이다.** 두 단계는 두 사다리 모두 실패 0 이고,
읽으려는 것(자원이 마르는 순서, 돈이 맞는지)은 거기서 이미 다 드러난다.

# 트랜잭션을 분리한 뒤

10절이 가리킨 1번을 했다. **PG 호출을 트랜잭션 밖으로 밀어냈고, 선차감도 빼냈다.**

```
tx1  payment(PENDING) + 주문 확정 + (포인트면 즉시 결제 → 재고 차감)   커밋
---  PG 호출                                                         트랜잭션 밖
tx2  결과 반영
     콜백 SUCCESS → 결제 SUCCESS + 재고 차감
```

두 가지가 달라졌다.

| | 전 | 후 |
| --- | --- | --- |
| PG 호출 | 확정 트랜잭션 안 | 커밋 뒤 |
| 재고 | 결제 **전**에 깎음 (선차감) | 결제가 SUCCESS 가 될 때 깎음 |

PG 호출이 실패해도 결제 기록이 남고, 재고는 애초에 빠지지 않는다.
**되돌릴 것이 없으므로 보상도 없다.**

포인트는 트랜잭션 밖으로 빼지 않았다. 외부가 아니라 우리 DB 라 뺄 이유가 없고,
잔액이 부족하면 전부 되돌아가는 기존 계약이 그대로 지켜진다.
"외부를 부르는가" 는 `PaymentStrategy.external` 이 들고 있다.
