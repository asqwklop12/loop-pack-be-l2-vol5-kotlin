# 결제 한 흐름 부하 — 주문부터 콜백까지

앞선 측정들은 **PG 가 고장났을 때** 우리가 어떻게 무너지는지 쟀다.
이 문서는 반대쪽을 잰다 — **PG 가 정상일 때 한 흐름이 끝까지 도는가,**
그리고 **돈이 맞는가.**

한 흐름은 이렇게 돈다.

```
주문 생성 → 주문 확정(카드) → PG 접수(202 PENDING) → PG 확정 → 콜백 → SUCCESS / FAILED
```

앞의 네 단계는 동기다. 마지막 두 단계는 PG 가 **나중에** 콜백으로 알려준다.
그래서 부하가 끝난 직후에 결제 테이블을 세면 **전부 PENDING** 이다.
콜백이 수렴할 때까지 기다린 뒤에 세야 성공·실패 숫자가 나온다.

## 1. 측정 환경

| 항목 | 값 |
| --- | --- |
| 날짜 | 2026-10-21 |
| PG | `pg-simulator` 0.5.0 · `PG_RESPONSE_DELAY=0s` · `PG_CALLBACK_DELAY=3s` |
| 거절 확률 | 한도 0.5% · 잔액 0.5% · 분실 0.1% (합 1.1%) |
| 대상 | `commerce-api` · 포트 8099 (관리 8098) |
| PG 타임아웃 | connect 1s · read 3s |
| 커넥션 풀 | HikariCP 40 · `connection-timeout: 3000ms` |
| 톰캣 | threads 200 |
| 결제 수단 | 카드 · 정상 카드(`...1451`) |
| 부하 | k6 · 30초 · 세 레인(결제 / 상품목록 / 404) |
| 초기화 | 단계마다 `orders` · `order_line` · `payment` truncate |

## 3. 읽은 것

### 결제는 가볍고, 남의 API 가 먼저 느려진다

VU 10 에서 확정은 med 24ms 인데 상품 목록은 한가할 때 540ms 짜리가 **1,159ms** 가 됐다.
결제 레인이 쓴 것은 자기 응답 시간이 아니라 **남이 쓸 DB 시간**이다.

### 무너지는 순서가 자원 순서다

세 레인을 따로 쏜 이유가 여기서 값을 한다.

| VU | 404 | 읽은 것 |
| ---: | ---: | --- |
| 10 | 1.4ms | DB 만 밀린다. 스레드는 한가하다 |
| 100 | 1.2ms | **커넥션 풀이 먼저 마른다** (40/40 · 대기 72). 스레드는 112/200 |
| 1,000 | **698ms** | 스레드까지 말랐다 (200/200). DB 를 안 타는 경로도 끌려 내려간다 |
| 10,000 | 526ms | 커넥션을 **못 받는다** (획득 실패 1,341). 요청의 99.3% 가 실패 |

순서가 분명하다 — **DB 시간 → 커넥션 풀 → 톰캣 스레드 → 전면 실패.**
커넥션이 스레드보다 먼저 마르는 것은 앞선 느린-PG 측정과 같은 결론이다.

### VU 10,000 은 숫자가 뒤집힌다

확정 med 가 34ms 로 **VU 100 보다 빠르다.** 빨라진 게 아니다.
주문 생성에서 118,916건이 거절돼서, 확정까지 간 450건은
**경쟁자가 다 떨어져 나간 뒤에 들어간 요청**이다.

그래서 이 단계의 응답 시간은 읽을 값이 아니다. 읽을 값은 두 개다 —
**처리율 571 → 7 /s** 와 **커넥션 획득 실패 0 → 1,341.**
부하 장치도 이 구간에서는 같이 한계라, 숫자가 대상만 재는 게 아니다.

### 콜백이 같이 밀린다 — 이게 새로 보인 것

콜백 처리율이 **894 → 344 → 173 /s** 로 떨어진다.
PG 의 콜백 발신은 **단일 스레드 직렬**이고, 한 건마다 우리 API 로 POST 를 쏜다.
우리 API 가 포화되면 그 POST 가 느려지고, **뒤에 줄 선 콜백 전부가 같이 밀린다.**

VU 1,000 에서는 부하가 끝난 뒤 **105초** 동안 결제가 미확정으로 남아 있었다.
주문은 이미 CONFIRMED 인데 결제는 PENDING 인 창이 2분 가까이 열려 있었다는 뜻이다.
돈은 결국 맞았지만, **맞기까지 걸린 시간**이 부하에 비례해 늘어난다.

여기서 나오는 말은 하나다 — 콜백은 **늦게 올 수 있다**는 전제를 깔아야 한다.
"확정은 콜백이 온다" 가 아니라 "콜백이 안 오면 조회로 대조한다" 가 필요한 이유다.

## 4. 어디까지 쓸 수 있나

| VU | 상태 |
| ---: | --- |
| 10 | 멀쩡하다. 자원 10% 아래 |
| 100 | **커넥션 풀이 한계**. 상품 목록 1.6초. 아직 돈은 다 맞는다 |
| 1,000 | 스레드까지 한계. 주문 생성 2,229건 거절. 콜백 2분 지연 |
| 10,000 | 무너진다. 요청의 99.3% 실패 |

**실질 천장은 VU 100 과 1,000 사이**다. 100 에서 이미 커넥션 풀이 마르고,
1,000 에서는 결제와 무관한 404 까지 끌려 내려간다.

## 5. 걸린 것 — truncate 와 PG 의 기억

첫 VU 10 에서 DRAFT 로 남은 주문 1건은 PG 가 **409** 로 거절한 건이다.
원인은 측정 쪽에 있었다.

`orders` 를 truncate 하면 auto_increment 가 1부터 다시 시작한다.
그런데 **PG 는 orderId 를 메모리에 들고 있다.** 직전에 손으로 돌려본
주문 1번(65,354원)이 남아 있어서, 같은 1번에 다른 금액이 들어오자
"같은 주문에 다른 금액" 으로 거절했다.

PG 의 멱등 장치가 제대로 동작한 것이고 고칠 쪽은 측정 절차다 —
**단계마다 PG 컨테이너도 같이 재기동해 저장소를 비운다.** 이후 단계는 그렇게 쟀다.

이게 실제 설계에 주는 말도 있다. 우리 쪽에서 orderId 를 재사용하면
PG 는 그것을 **같은 거래의 재시도로 읽는다.** 주문 번호는 지우고 다시 쓸 수 있는
번호가 아니다.

> **측정 주의.** VU 1,000 의 수렴 대기는 한 번 잘못 읽었다. PENDING 이 10,857 에서
> 두 번 같은 값으로 읽혀 "멈췄다" 고 판단했는데, 실제로는 단일 스레드가 느린 POST 에
> 걸려 **뭉쳐서 빠지는** 중이었다. 같은 값이 몇 번 나왔다고 끝난 게 아니다.

# 고장 — PG 가 10초 걸릴 때

여기부터는 같은 사다리를 **`PG_RESPONSE_DELAY=10s`** 로 다시 올린다.
PG 는 죽지 않았다. **살아 있는데 느리다.**

우리 read 타임아웃은 3초다. PG 는 10초에 답한다. 그래서 **모든 카드 결제가 끊긴다.**
끊기면 확정 트랜잭션이 롤백되고 `payment` 행도 사라진다 — **그런데 PG 는 그 결제를 들고 있다.**

그래서 이 측정은 우리 쪽만 세면 안 된다. **PG 쪽에 남은 거래까지 세야** 구멍이 보인다.
`GET /api/v1/payments?orderId=` 로 주문 번호를 1부터 끝까지 훑어서 셌다.

## 6. 돈이 어디로 갔나

| VU | 주문 | 확정 | 우리 `payment` 행 | 우리가 받은 돈 | PG 거래 | PG SUCCESS | **PG 가 승인한 금액** |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 10 | 100 | **0** | **0** | **0원** | 100 | 98 | **6,245,829원** |
| 100 | 633 | **0** | **0** | **0원** | 437 | 431 | **27,188,855원** |
| 1,000 | 1,720 | **0** | **0** | **0원** | 700 | 690 | **43,976,140원** |
| 10,000 | 9,163 | **0** | **0** | **0원** | 2,127 | 2,112 | **134,735,513원** |

주문은 전부 DRAFT 로 남고, 우리 결제 기록은 **네 단계 모두 0행**이다.
정상 PG 에서 미확정이 0 이었던 것과 숫자는 같은데, 뜻이 정반대다 —
그때는 **다 확정됐다**는 0 이고, 지금은 **아무것도 기록되지 않았다**는 0 이다.

그리고 PG 쪽에는 **승인된 결제가 쌓여 있다.** VU 10 에서도 98건 · 624만원이다.
가장 작은 부하에서도 그렇다.

**이게 이번 주차가 막으려는 사고다.** 롤백은 우리 DB 만 되돌린다.
남의 시스템에 이미 넘어간 승인은 되돌려주지 않는다.

## 7. 속도

| VU | 주문 생성 med | 주문 확정 med | 상품 목록 med | 404 med |
| ---: | ---: | ---: | ---: | ---: |
| 10 | 8.5ms | **3,011ms** | 519ms | 2.2ms |
| 100 | 703ms | 3,691ms | 6,691ms | 2.1ms |
| 1,000 | 30ms | 14,989ms | 15,001ms | **11,218ms** |
| 10,000 | 10,075ms | 30,716ms | 25,030ms(p95) | 16,061ms(p95) |

확정 med 가 VU 10 에서 이미 **3,011ms** 다. 타임아웃 3초에 정확히 붙었다.
**모든 결제가 3초를 꽉 쓰고 실패한다.**

VU 1,000 에서는 확정이 15초다. 타임아웃이 3초인데 15초가 걸리는 이유는
PG 를 기다린 게 아니라 **그 앞에서 커넥션과 스레드를 기다린** 시간이다.

| VU | 톰캣 busy | 히카리 active | 풀 대기 | 커넥션 획득 실패 |
| ---: | ---: | ---: | ---: | ---: |

| 1,000 | **200 / 200** | 40 / 40 | 160 | **1,542** |

정상 PG 와 나란히 놓으면 **고장이 단계를 한 칸씩 끌어내린** 것이 보인다.

| 지표 | 정상 PG | 10초 PG |
| --- | --- | --- |

결제 하나가 커넥션을 3초씩 쥐고 있으니, 40개 풀로는 초당 13건밖에 못 돌린다.

## 9. 읽은 것

### 느린 PG 는 죽은 PG 보다 나쁘다 — 다시 확인

PG 가 죽으면 연결이 즉시 거부돼 커넥션을 쥐는 시간이 짧다.
느리면 **3초씩 쥐고 있다.** 필요한 자리가 그만큼 늘어난다.

```
필요한 커넥션 = 결제 처리율 × 커넥션 점유시간
```

VU 100 에서 우리는 초당 약 21건을 확정 시도했고, 한 건이 3초를 쥐었다.
21 × 3 = **63개** 가 필요한데 풀은 **40개**다. 그래서 278건이 커넥션을 못 받았다.

### 롤백은 우리 쪽 거짓말이다

우리 장부는 깨끗하다 — 주문 DRAFT, 결제 0행, 받은 돈 0원. 모순이 없다.
**PG 장부에는 1억 3천만원이 승인돼 있다.**

양쪽 장부가 각자 일관된데 서로 다르다. 이걸 찾아내는 방법은 하나뿐이다 —
**대조(reconciliation).** PG 에 조회를 걸어 우리가 모르는 거래를 찾아오는 것.
이번 측정에서 내가 `orderId` 로 PG 를 훑은 그 행위가 바로 대조다.
지금은 측정 스크립트가 손으로 했고, 코드에는 없다.

### 콜백은 허공으로 떨어졌다

PG 는 3초 뒤 결제를 확정하고 우리에게 콜백을 보냈다.
우리 `PaymentCallbackHandler` 는 그 주문의 PENDING 결제를 찾는데,
**롤백돼서 행이 없다.** 그래서 아무것도 하지 않고 끝난다.

터지지는 않는다(그 경로는 테스트로 막아 뒀다). 하지만 **콜백이 가져온 정보가 버려진다.**
PG 는 "이 주문 승인했다" 고 알려줬는데 우리는 들을 그릇이 없었다.

여기서 순서가 나온다. **결제 기록을 먼저 남기고 PG 를 불러야 한다.**
지금은 한 트랜잭션 안에서 둘을 같이 하니, PG 호출이 실패하면 기록도 같이 사라진다.

## 10. 그래서 고칠 순서

측정이 가리키는 순서는 이렇다.

| 순서 | 할 일 | 이 측정이 주는 근거 |
| ---: | --- | --- |
| 1 | **트랜잭션 분리** — 결제 기록을 먼저 커밋하고 PG 호출 | 롤백으로 기록이 사라져 `payment` 0행 · 콜백이 허공으로 |
| 2 | **타임아웃 축소** | 3초가 커넥션 점유시간이다. 21 × 3 = 63 > 40 |
| 3 | **서킷** | VU 100 에서 이미 100% 실패. 끊어도 잃을 게 없다 |
| 4 | **조회 대조** | PG 에 1억 3천만원이 떠 있고 우리는 모른다 |

1번이 먼저인 이유가 있다. 2번의 계산식(`처리율 × 점유시간`)은
**커넥션을 PG 대기 중에 쥐고 있다**는 전제 위에 서 있다.
트랜잭션을 분리하면 그 전제가 사라지므로, 타임아웃 값을 먼저 정해봐야 다시 정해야 한다.

> **측정 주의.** 부하를 끊어도 서버는 계속 처리한다. VU 10,000 에서 k6 가 멈춘 뒤에도
> 주문이 8,215 → 9,163 으로, PG 거래가 793 → 2,127 로 늘었다.
> 톰캣 수용 큐에 쌓여 있던 요청이 뒤늦게 실행된 것이다.
> **k6 가 끝난 시점에 센 숫자는 최종값이 아니다.** 위 표는 수렴한 뒤에 다시 센 값이다.
