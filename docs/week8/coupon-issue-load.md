## 맞게 동작하면 이렇게 보여야 한다

요청 1000건이 한도 119 를 넘으므로 아래 네 숫자가 모두 한도와 같아야 한다.

| 어디서 보나                                  | 기대값            |
| -------------------------------------------- | ----------------- |
| k6 `issue_201`                               | 119               |
| k6 `issue_400`                               | 1000 - 119 = 881  |
| `select count(*) from coupon where campaign_id = 2` | 119        |
| `select issued_count from campaign where id = 2`    | 119        |

`count(distinct user_id)` 도 쿠폰 수와 같아야 한다. 다르면 한 사람이 두 장을 가진 것이다.

k6 의 `http_req_failed` 는 400 을 실패로 센다. 여기서는 품절 거절이 881건이면 88.1% 가 정상이다.

4차부터는 자리가 없으면 429 로 거절하므로 201 이 119 가 아니어도 틀린 것이 아니다. 대신 아래가 서로 같아야 한다.

- k6 `issue_201` = `coupon` 행 수 = `count(distinct user_id)` = `issued_count`
- 5차부터는 레디스 `HLEN campaign:2:issued` 도 같은 값
- 끝난 뒤 세마포어 키(4차)나 `SCARD coupon:issue:permits`(5차부터)는 0

## 1차 — 한도 119 에 1000장이 나갔다

발급 수 증가가 엔티티를 읽고 메모리에서 +1 한 값을 덮어쓰는 방식이었고 락이 없었다. 동시에 들어온 요청들이
같은 `issued_count` 를 읽고 각자 덮어써서 974번의 증가가 사라졌다. 발급 수가 계속 한도 아래로 보이니 품절 검사가
한 번도 걸리지 않았다.

쿠폰 행은 `(campaign_id, user_id)` 유니크 키로 사용자당 한 장만 막는다. 서로 다른 사용자 사이의 총량은 막지 못한다.

## 2차 — 조건부 업데이트로 한도에서 멈췄다

```sql
update campaign
   set issued_count = issued_count + 1
 where id = ?
   and issued_count + 1 <= total_limit
```

DB 가 행을 바꾸는 순간에 한도를 확인하므로 동시에 들어와도 한도를 넘는 증가는 0행으로 끝난다. 0행이면 품절로 400 을 준다.
네 숫자가 모두 119 로 맞았다.

p95·p99 가 1차보다 늘었다. 같은 캠페인 행을 바꾸려는 요청이 그 행 락을 차례로 기다리기 때문으로 보지만 따로 확인하지는 않았다.

## 3차 — 인스턴스 3대에서도 한도에서 멈췄다

한도 판정은 앱 메모리가 아니라 DB 의 update 한 문장에서 일어난다. 인스턴스가 몇 대든 같은 MySQL 의 같은 캠페인 행 락을
차례로 잡으므로 결과가 2차와 같다. 사용자당 한 장도 DB 유니크 키가 막으니 인스턴스 수와 상관없다.

평균 지연은 조금 줄었지만 p95·p99 는 늘었다. 앱이 늘어 동시에 DB 에 닿는 요청은 많아졌는데, 병목인 캠페인 행은 여전히
하나라서 꼬리가 길어진 것으로 본다. 한 번 돌린 결과라 확정은 아니다.

앱을 늘리면 DB 커넥션도 같이 는다. 인스턴스당 풀이 40 이라 3대면 최대 120개인데, MySQL `max_connections` 는 151 이다.
몇 대만 더 늘려도 앱보다 DB 커넥션이 먼저 막힌다.

## 4차 — 세마포어를 넣자 처음 3명만 받았다

흐름은 기존 쿠폰 조회 → 캠페인 조회 → 세마포어 `INCR` (3 넘으면 `DECR` 하고 429) → 조건부 업데이트·쿠폰 저장 → 커밋 뒤 `DECR` 이다.
루아 없이 `INCR`·`DECR` 만 쓴다.

같은 조건으로 두 번 돌렸고 두 번 다 201 3건, 429 997건이었다. 두 번째 지연은 166 / 368 / 430ms 였다.
쿠폰 행과 `issued_count` 는 같았고, 끝난 뒤 세마포어 키는 0 으로 돌아왔다. 한도는 지켰지만 처음 3명 뒤로는 아무도 자리를 잡지 못했다.

두 번째 실행 중에 키 값을 2ms 마다 읽었다. 0 이 아닌 표본 약 390개 중 대부분이 28~45 였고, 1~3 은 두 번뿐이었다.

거절될 요청도 먼저 `INCR` 을 하고, 판정한 뒤에야 `DECR` 을 한다. 동시 요청이 100개면 그 사이에 있는 요청이 늘 수십 개라 카운터가
실제 자리 수보다 크게 부풀어 있다. 처음 3명이 반납해도 다음 요청이 받는 값은 30 언저리라 거절된다. 이 틈은 미리 알고 받아들였는데,
동시 100 에서는 가끔 생기는 일이 아니라 발급을 막아버렸다.

429 도 평균 160ms 안팎이 걸렸다. 기존 쿠폰 조회와 캠페인 조회가 세마포어보다 앞에 있어서 거절된 997건도 DB 를 두 번씩 읽고 거절된다.
DB 부하는 줄지 않았다.

## 5차 — 레디스로 앞단을 걸러도 토큰 Set 이 부풀어 발급이 막혔다

4차 세마포어를 걷어내고 아래 설계로 다시 만들었다. 레디스는 전부 primary 만 쓴다.

| 단계 | 어디서 | 명령 | 빠지는 응답 | 레디스 장애일 때 |
| ---- | ------ | ---- | ----------- | ---------------- |
| ① 기존 쿠폰 | 레디스 | `HGET campaign:{id}:issued userId` | 200 | 건너뜀 |
| ② 품절 | 레디스 | `EXISTS campaign:{id}:soldout` | 400 | 건너뜀 |
| ③ 기간·발급 가능 | 레디스, 없으면 DB 에서 읽어 채움 | `HGETALL campaign:{id}` | 404 · 400 | 건너뜀 |
| ④ 세마포어 | 레디스 | 토큰(UUID) `SADD` → `SCARD`, 3 넘으면 `SREM` | 429 | 503, DB 발급 안 함 |
| ⑤ 발급 트랜잭션 | MySQL | 조건부 업데이트 + 쿠폰 저장, 품절이면 ② 표시를 남김 | 201 · 400 | - |
| ⑥ 반환 | 레디스 | `SREM` 자기 토큰, 201 이면 `HSET issued` | - | 쿠폰은 유지 |

①②③ 을 건너뛰어도 ⑤ 가 DB 에서 기간·발급 가능·한도·중복을 다시 판정한다.

세 번 돌렸다. 201 은 3건, 0건, 2건이었다. 세 번 다 쿠폰 행·사용자 수·`issued_count`·레디스 발급 기록이 같았고,
끝난 뒤 토큰은 0개였다. 레디스 장애로 건너뛴 로그는 없었다. 두 번째 지연은 78 / 120 / 141ms 였다.

세 번째 실행 중에 `SCARD coupon:issue:permits` 를 2ms 마다 읽었다. 0 이 아닌 표본 478개 중 대부분이 25~37 이었고 3 이하는 41개였다.

원인은 4차와 같다. 거절될 요청도 먼저 `SADD` 하고 `SCARD` 로 판정한 뒤에야 `SREM` 한다. 카운터가 토큰 Set 으로 바뀌었을 뿐
그 사이에 걸린 요청 수십 개가 Set 을 부풀리는 틈은 그대로다.

달라진 것은 거절 비용이다. 4차의 429 는 DB 를 두 번 읽고 나서 나갔지만 5차는 레디스에서 끝난다. 평균 지연이 4차보다 짧았다.

쿠폰은 한도·사용자당 한 장 모두 맞았다. 늘어난 것은 큐 길이다. 202 를 받은 사용자가 결과를 보려고 다시 요청하면
①에 아직 발급 기록이 없으므로 ④에서 또 `LPUSH` 된다. 대기 여부를 보지 않으니 다시 확인한 횟수만큼 같은 요청이 큐에 쌓였다.

워커는 그 중복을 하나씩 꺼내 발급 트랜잭션을 연다. 이미 받은 사용자는 유니크 제약(MySQL 1062)에 걸려 트랜잭션째
되돌아가므로 쿠폰·발급 수는 늘지 않지만, 아직 못 받은 사용자의 요청은 그 뒤에 줄을 선다. 초당 발급이 8차보다 낮고
사용자당 시도가 늘어난 이유로 본다.

부하가 끝난 뒤에도 남은 75439 건을 워커 3개가 초당 100 건 남짓으로 비우고 있었다(약 12분 분량). 1062 오류 로그가 계속
찍혀 실행 뒤 큐 키를 지웠다. 그 사이 쿠폰·발급 수는 1000 그대로였다.

실행 중 워커가 레디스 연결에 실패한 경고가 인스턴스 하나에서 15번 찍혔다. `BRPOP` 은 꺼내기 전에 실패하므로 요청이 사라지지는 않는다.
