## 맞게 동작하면 이렇게 보여야 한다

요청 1000건이 한도 119 를 넘으므로 아래 네 숫자가 모두 한도와 같아야 한다.

| 어디서 보나                                  | 기대값            |
| -------------------------------------------- | ----------------- |
| k6 `issue_201`                               | 119               |
| k6 `issue_400`                               | 1000 - 119 = 881  |
| `select count(*) from coupon where campaign_id = 2` | 119        |
| `select issued_count from campaign where id = 2`    | 119        |

`count(distinct user_id)` 도 쿠폰 수와 같아야 한다. 다르면 한 사람이 두 장을 가진 것이다.

k6 의 `http_req_failed` 는 400 을 실패로 센다. 여기서는 품절 거절이 881건이면 88.1% 가 정상이다.

## 결과

| 항목                  | 1차: 락 없이 읽고 +1 해서 씀     | 2차: 조건부 업데이트              |
| --------------------- | -------------------------------- | --------------------------------- |
| 201                   | 1000                             | 119                               |
| 400                   | 0                                | 881                               |
| `coupon` 행           | 1000 (사용자 1000명)             | 119 (사용자 119명)                |
| 캠페인 `issued_count` | 26                               | 119                               |
| 지연 avg / p95 / p99  | 206 / 360 / 392ms                | 157 / 487 / 578ms                 |

## 1차 — 한도 119 에 1000장이 나갔다

발급 수 증가가 엔티티를 읽고 메모리에서 +1 한 값을 덮어쓰는 방식이었고 락이 없었다. 동시에 들어온 요청들이
같은 `issued_count` 를 읽고 각자 덮어써서 974번의 증가가 사라졌다. 발급 수가 계속 한도 아래로 보이니 품절 검사가
한 번도 걸리지 않았다.

쿠폰 행은 `(campaign_id, user_id)` 유니크 키로 사용자당 한 장만 막는다. 서로 다른 사용자 사이의 총량은 막지 못한다.

## 2차 — 조건부 업데이트로 한도에서 멈췄다

```sql
update campaign
   set issued_count = issued_count + 1
 where id = ?
   and issued_count + 1 <= total_limit
```

DB 가 행을 바꾸는 순간에 한도를 확인하므로 동시에 들어와도 한도를 넘는 증가는 0행으로 끝난다. 0행이면 품절로 400 을 준다.
네 숫자가 모두 119 로 맞았다.

p95·p99 가 1차보다 늘었다. 같은 캠페인 행을 바꾸려는 요청이 그 행 락을 차례로 기다리기 때문으로 보지만 따로 확인하지는 않았다.
