# 쿠폰 발급 100 VU

## 조건

- 2026-11-08, 로컬 `commerce-api` (`local` 프로필), 로컬 MySQL
- 캠페인 2, 총 발급 한도 119, 시작 전 발급 수 0, 쿠폰 0장. 두 번째 실행 전에 쿠폰을 지우고 발급 수를 0 으로 되돌렸다
- k6 `shared-iterations`, 100 VU, 1000회. 회차마다 다른 사용자(`X-USER-ID` 100000~100999)
- 3차는 같은 jar 를 8080·8083·8084 세 인스턴스로 띄우고 회차 번호 순서로 번갈아 보냈다. 인스턴스마다 커넥션 풀 40

```
CAMPAIGN_ID=2 k6 run docs/week8/k6-coupon-issue.js
CAMPAIGN_ID=2 BASE_URLS=http://localhost:8080,http://localhost:8083,http://localhost:8084 k6 run docs/week8/k6-coupon-issue.js
```

## 맞게 동작하면 이렇게 보여야 한다

요청 1000건이 한도 119 를 넘으므로 아래 네 숫자가 모두 한도와 같아야 한다.

| 어디서 보나                                  | 기대값            |
| -------------------------------------------- | ----------------- |
| k6 `issue_201`                               | 119               |
| k6 `issue_400`                               | 1000 - 119 = 881  |
| `select count(*) from coupon where campaign_id = 2` | 119        |
| `select issued_count from campaign where id = 2`    | 119        |

`count(distinct user_id)` 도 쿠폰 수와 같아야 한다. 다르면 한 사람이 두 장을 가진 것이다.

k6 의 `http_req_failed` 는 400 을 실패로 센다. 여기서는 품절 거절이 881건이면 88.1% 가 정상이다.

## 1차 — 한도 119 에 1000장이 나갔다

발급 수 증가가 엔티티를 읽고 메모리에서 +1 한 값을 덮어쓰는 방식이었고 락이 없었다. 동시에 들어온 요청들이
같은 `issued_count` 를 읽고 각자 덮어써서 974번의 증가가 사라졌다. 발급 수가 계속 한도 아래로 보이니 품절 검사가
한 번도 걸리지 않았다.

쿠폰 행은 `(campaign_id, user_id)` 유니크 키로 사용자당 한 장만 막는다. 서로 다른 사용자 사이의 총량은 막지 못한다.

## 2차 — 조건부 업데이트로 한도에서 멈췄다

```sql
update campaign
   set issued_count = issued_count + 1
 where id = ?
   and issued_count + 1 <= total_limit
```

DB 가 행을 바꾸는 순간에 한도를 확인하므로 동시에 들어와도 한도를 넘는 증가는 0행으로 끝난다. 0행이면 품절로 400 을 준다.
네 숫자가 모두 119 로 맞았다.

p95·p99 가 1차보다 늘었다. 같은 캠페인 행을 바꾸려는 요청이 그 행 락을 차례로 기다리기 때문으로 보지만 따로 확인하지는 않았다.

## 3차 — 인스턴스 3대에서도 한도에서 멈췄다

한도 판정은 앱 메모리가 아니라 DB 의 update 한 문장에서 일어난다. 인스턴스가 몇 대든 같은 MySQL 의 같은 캠페인 행 락을
차례로 잡으므로 결과가 2차와 같다. 사용자당 한 장도 DB 유니크 키가 막으니 인스턴스 수와 상관없다.

평균 지연은 조금 줄었지만 p95·p99 는 늘었다. 앱이 늘어 동시에 DB 에 닿는 요청은 많아졌는데, 병목인 캠페인 행은 여전히
하나라서 꼬리가 길어진 것으로 본다. 한 번 돌린 결과라 확정은 아니다.

앱을 늘리면 DB 커넥션도 같이 는다. 인스턴스당 풀이 40 이라 3대면 최대 120개인데, MySQL `max_connections` 는 151 이다.
몇 대만 더 늘려도 앱보다 DB 커넥션이 먼저 막힌다.
